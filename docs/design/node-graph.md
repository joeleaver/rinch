# Node Graph Editing — `rinch-graph-core` + `rinch-graph-view`

**Status:** Proposed (2026-10-29). Nothing built yet.
**Scope:** a foundation for node-and-wire editors built on rinch: shader and
material graphs, flowcharts, org charts, audio routing, state machines. Two new
crates in this workspace, opt-in behind a `graph` feature on `rinch`.

## Why

Several apps have needed the same thing: a pannable, zoomable canvas of boxes
joined by wires, where the user drags nodes, draws connections between ports,
selects, deletes and undoes. Rinch has the pieces (`Drag`, `bounding_rect`,
SVG paths, keyed `for`, fine-grained signals), but every app that assembles
them re-solves the same hard parts:

- hit-testing and dragging under a zoomed transform,
- where a port is on screen, so a wire can end there,
- drawing a new connection and deciding what it may connect to,
- keeping 500 nodes cheap when one moves,
- undo that covers all of the above.

Those belong in one place. What is inside a node does not: a shader node, an
org-chart card and a flowchart diamond have nothing in common but the frame.

## Decision

1. **Two crates in this workspace**, mirroring the editor's split
   (`rinch-editor-core` / `rinch-editor-view`):
   - `rinch-graph-core` — the pure model. No rinch dependency, wasm-clean,
     unit-testable without a document.
   - `rinch-graph-view` — the canvas, built on rinch, desktop and web.
2. **Not in `rinch` itself or its default prelude.** It is a domain widget, like
   the rich-text editor. `rinch` gains a `graph` feature that re-exports it.
3. **Not a separate repository.** Inside the workspace, the crates get clippy,
   tests, the perf baselines and the batch CI, so a rinch change that breaks
   them fails in the PR that made it. The earlier attempt
   ([rinchflow](#prior-art-rinchflow)) lived outside the repository against a
   path dependency and stopped tracking rinch after its first commit.
4. **The app owns node bodies.** A node is the app's own rsx component; the
   library renders the frame, the ports and the wires around it.
5. **Built against two real consumers, not a feature list.** v1 is done when two
   apps with different needs run on it (below).

## The two consumers that set the API

The design is checked against two apps at opposite ends:

| | Typed-port graph (shader / material / audio) | Layout-heavy graph (org chart / flowchart) |
|---|---|---|
| Ports | many, typed, fixed per node kind | few or implicit (top/bottom) |
| Connections | type-checked, usually acyclic, one wire per input | free, often a tree |
| Node position | user places it | mostly computed by a layout pass |
| Node body | dense controls (sliders, color pickers, previews) | text card, avatar |
| Scale | tens to low hundreds of nodes | hundreds to thousands |

A feature goes into the library only when both need it, or when one needs it
and it cannot be built outside. Everything else is an extension point.

## `rinch-graph-core` — the model

### Types

```rust
pub struct NodeId(u64);   // stable, Copy, generated by the graph
pub struct PortId(u64);
pub struct EdgeId(u64);

pub enum PortDir { In, Out }

pub struct Port<P> {
    pub id: PortId,
    pub node: NodeId,
    pub dir: PortDir,
    pub data: P,              // app's port payload: a type tag, a label
}

pub struct Node<N> {
    pub id: NodeId,
    pub pos: Point,           // graph space, not screen space
    pub ports: Vec<PortId>,   // ordered
    pub data: N,              // app's node payload
}

pub struct Edge<E> {
    pub id: EdgeId,
    pub from: PortId,         // always an Out port
    pub to: PortId,           // always an In port
    pub data: E,
}

pub struct Graph<N, P, E> { /* slotmaps keyed by id, plus port→edges index */ }
```

IDs are integers, not strings: rinchflow's `String` IDs cloned on every lookup,
and an app that needs a stable external key keeps it in `N`.

### Rules

The app supplies a `Rules` implementation. The graph consults it on every
connection attempt, both for the live preview while dragging and for the commit:

```rust
pub trait Rules<N, P, E> {
    /// May `from` connect to `to`? Called while a wire is being dragged, for
    /// every candidate port, so it must be cheap.
    fn can_connect(&self, g: &Graph<N, P, E>, from: PortId, to: PortId) -> Verdict;
    /// How many edges may end at this input. Default: 1.
    fn max_inputs(&self, port: &Port<P>) -> Option<usize> { Some(1) }
    /// Reject a connection that would close a cycle. Default: true.
    fn acyclic(&self) -> bool { true }
}

pub enum Verdict { Allow, Replace(EdgeId), Deny }
```

`Replace` covers the common case of dropping onto an occupied single input: the
old wire is removed in the same step. A shader graph implements
`can_connect` as a type-compatibility check; an org chart allows everything and
turns `acyclic` on.

### Steps and history

Every change is a `Step`, the same model the editor uses:

```rust
pub enum Step<N, P, E> {
    AddNode(Node<N>, Vec<Port<P>>),
    RemoveNode(NodeId),            // invert carries the node, ports and edges
    MoveNodes(Vec<(NodeId, Point, Point)>),  // from, to
    Connect(Edge<E>),
    Disconnect(EdgeId),
    SetNodeData(NodeId, N, N),     // old, new
    SetEdgeData(EdgeId, E, E),
    // ports added/removed at runtime (a node whose inputs depend on a setting)
    AddPort(Port<P>), RemovePort(PortId),
}
```

A `Transaction` is a list of steps applied together. Each step's inverse is
derived when it is applied, so undo is generic. A whole drag is one
transaction: the view moves nodes live without recording, then records a single
`MoveNodes` on release.

Selection lives in the model state (`GraphState { graph, selection }`), as the
editor keeps selection in `EditorState`, so undo can restore it.

### Not in core

- **Rendering, geometry of ports, viewport.** Core knows a node's position, not
  its size: size is decided by layout.
- **Layout algorithms.** See [Extensions](#extensions).
- **Evaluation.** A shader graph compiles itself to WGSL; a dataflow app runs
  its own scheduler. Core provides `topo_order()` and `upstream(node)` because
  every evaluator needs them, and nothing more.
- **Serialization.** `serde` derives behind a feature. The format is the app's.

## `rinch-graph-view` — the canvas

### Structure

```
GraphCanvas  (overflow: hidden; receives pan, zoom, marquee, keys)
└── world    (one element; transform: translate(x,y) scale(z))
    ├── <svg> edge layer   (one <path> per edge, keyed for)
    ├── node layer         (one absolutely-positioned frame per node, keyed for)
    │   └── frame: ports + the app's body component
    └── overlay            (in-progress wire, marquee rectangle)
```

The viewport is one `transform` on one element, so panning and zooming write a
single style and lay nothing out again. Every node and edge sits in graph space
under it.

### The reactive store

The view does not read `Graph` directly in effects. It mirrors what rendering
needs into per-item signals (rinchflow had this part right):

- `node_ids: Signal<Vec<NodeId>>` drives the keyed `for` for nodes; likewise
  `edge_ids`.
- Each node has its own `pos: Signal<Point>`, `selected: Signal<bool>`, and a
  `size: Signal<Size>` filled from layout.
- Each edge's path effect reads only its two endpoints' port positions.

Moving one node writes one signal, and only that node's frame and its own
edges update. A perf baseline in the crate pins this: drag one node in a
200-node graph, assert the counters for one frame.

The store applies core transactions and patches the signals from the steps,
so the model and the mirror cannot drift apart.

### The app's API

```rust
let graph = GraphHandle::new(Graph::new(), MyRules);

rsx! {
    GraphCanvas {
        handle: graph.clone(),
        // The app renders the inside of each node. Called once per node,
        // when the node first appears; it reads the node's signals itself.
        node: move |id: NodeId| rsx! { ShaderNodeBody { handle: graph.clone(), id } },
        // Optional: where each port sits on the frame, and how it looks.
        port: move |id: PortId| rsx! { TypedPortDot { handle: graph.clone(), id } },
        // Optional: the edge's path between two points. Default: horizontal bezier.
        edge_path: EdgePath::Bezier,
        on_connect: move |from, to| { /* after Rules allowed it */ },
    }
}
```

`GraphHandle` is the counterpart of `EditorHandle`: it owns the state, applies
transactions, exposes history (`undo`, `redo`), selection and viewport
(`fit_view`, `zoom_to`, `screen_to_graph`).

### Port positions

A wire ends at a port, and where a port is depends on layout: the app's body
decides how tall a node is and where each row with a port sits. The view
therefore measures ports after layout instead of computing them:

- each port element is registered with the store;
- after a layout that changed any node's size, the view reads each affected
  port's `bounding_rect()`, converts it to graph space through the viewport,
  and writes the port's position signal;
- edge paths read those signals.

This needs a reliable "this element's box changed" notification from rinch,
which does not exist today (see [Prerequisites](#prerequisites-in-rinch)).
Until it does, the view re-measures a node's ports when that node's own
signals change and once per frame after an add, which covers most cases and
misses a body whose height changes on its own (an expanding text area).

### Interactions

| Gesture | Built on | Notes |
|---|---|---|
| Drag a node (and the selection) | `Drag::absolute`, divide deltas by zoom | live signal writes, one `MoveNodes` on release, `on_cancel` restores |
| Pan | `Drag` on the canvas background; wheel/trackpad scroll | middle-button and space+drag too |
| Zoom | ctrl+wheel and pinch, centred on the pointer | needs a wheel event (prerequisite) |
| Draw a wire | `Drag` from a port; candidates lit by `Rules::can_connect` | drop on a port commits; drop on empty canvas fires `on_connect_to_empty` (the "add node here" menu) |
| Re-route a wire | drag from an occupied input picks up the existing wire | |
| Marquee select | `Drag` on background with shift, or a mode | rectangle in graph space, intersect node rects |
| Select an edge | click near the path | see hit-testing prerequisite |
| Delete, copy, paste, select all, undo | the canvas element's own `onkeydown` | not a global keyboard interceptor (rinchflow used one, which fires while a node body's text input has focus) |
| Snap to grid | option on the handle | applied in the move, not stored separately |

Each interaction is a small state machine in its own module, so a new one
(edge reroute points, grouping) does not touch the others.

### Performance targets

- One node dragged in a 200-node graph: one node frame, its edges, nothing else.
- Pan or zoom: one style write, no layout of node bodies.
- 1,000 nodes on screen at rest: no per-frame work at all.
- Off-screen nodes are still mounted in v1. Virtualizing them (as the editor
  does) is a v2 item, only if a consumer hits it.

## Extensions

Kept outside the two crates, or as optional modules behind features, until a
second consumer needs them:

- **Auto-layout.** A `Layout` trait over core (`fn layout(&Graph, sizes) ->
  HashMap<NodeId, Point>`) and a `graph-layout-tree` module for the org chart.
  Layered (Sugiyama) layout for flowcharts later. Applying a layout is an
  ordinary `MoveNodes` transaction, so it undoes and can animate.
- **Minimap.** A second, small rendering of node rects; reads the same signals.
- **Groups / frames, reroute points, comments.** Each is a node kind the app
  defines, plus at most a small view hook.
- **Collaboration.** Steps are already the unit a CRDT adapter would project,
  as `rinch-editor-collab` does for the editor. Not designed further here.
- **Theming.** Frames, ports and wires use `--rinch-graph-*` CSS variables over
  the rinch theme.

## Prerequisites in rinch

Found while drafting. Each is its own issue, and none is specific to graphs.

1. **An element-level wheel event.** Rinch delivers `onscroll` (a container
   moved) but no `onwheel` carrying deltas and modifiers, so an app cannot
   zoom on ctrl+wheel or pan a non-scrolling canvas with a trackpad. Needed
   for zoom. Pinch on touch and trackpads would follow the same event.
2. **Notification when an element's box changes size** (a `ResizeObserver`
   equivalent, desktop and web). Needed to place wires on ports when a node's
   body changes size by itself. The workaround above covers v1.
3. **Hit-testing an SVG path by its stroke.** An `<svg>` is hit-tested as its
   box today, so a click anywhere in an edge's bounding rectangle would select
   it. To check: whether hit-testing descends into SVG shapes at all. The
   fallback is an invisible wide-stroke path per edge, or a distance test in
   the canvas's click handler against each edge's curve.
4. **Measure, don't guess:** `bounding_rect()` under a scaled ancestor answers
   the on-screen (scaled) box. The view divides by zoom to get graph space.
   Worth a test in the crate so a change to that rule is caught.

## Prior art: rinchflow

`~/dev/rinchflow` (one commit, 2026-03-12, about 4,000 lines) was a port of
xyflow (React Flow) to rinch. What to keep and what not:

| Keep | Drop |
|---|---|
| One signal per node field, so moving a node touches only that node | `String` node and edge IDs |
| Edges subscribing only to their two endpoints | Edges drawn as rotated `<div>` segments approximating a curve; use an SVG `<path>` |
| The edge-path math (`bezier`, `step`, `smoothstep`) — portable as-is | One 900-line store holding the graph, the viewport and drag state together |
| Multi-select drag capturing starting positions, deltas divided by zoom | A global keyboard interceptor for canvas shortcuts |
| Snap-to-grid in the move | xyflow's API shape (handles by string ID, props mirrored from React) |
| | No undo, no connection rules |

## Milestones

1. **Core.** Types, `Rules`, steps with inverses, transactions, history,
   `topo_order`. Unit tests, including undo of every step and the
   cycle/max-inputs rules. No rinch.
2. **Canvas skeleton.** `GraphCanvas`, viewport transform, node frames with app
   bodies, node drag, pan, selection, delete, undo. Perf baseline for a single
   node drag.
3. **Wires.** Port registration and measurement, SVG edge layer, drawing a
   wire with live `Rules` feedback, replace-on-occupied-input, re-routing.
4. **First consumer.** A small shader-graph example in `examples/` (typed
   ports, a WGSL preview through `RenderSurface`). Gaps found go back into 1–3.
5. **Second consumer.** An org-chart example with the tree-layout module. The
   API is not called stable until both examples run without workarounds.
6. **Web.** The same examples under `rinch-web`, with browser tests for drag,
   wire drawing and zoom in Chrome and Firefox.

Prerequisites 1 (wheel) and 3 (edge hit-testing) are needed by milestone 3;
2 (resize notification) can follow.

## Open questions

- **Which real apps are the two consumers?** The examples stand in for them,
  but an app with a deadline is a better test. Pick before milestone 2.
- **Name.** `rinch-graph` collides in spirit with charting. Alternatives:
  `rinch-nodes`, `rinch-flow`.
- **Port layout ownership.** Should ports be placed by the app's body (an
  input row renders its own port, most flexible) or by the frame (ports in a
  column on each side, simplest)? Proposal: support both, the frame's columns
  being the default `port` renderer.
- **Edges between nodes in different groups**, and edges that route around
  nodes, are left out of v1 entirely.
