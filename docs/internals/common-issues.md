# Common issues (layout/CSS behaviour that surprises)

Read this page when your task touches: a rendering surprise: inline-flex, UA stylesheet defaults, selects, inputs, tables, selectors, sizing keywords, empty divs.

Moved verbatim from `CLAUDE.md` on 2026-10-22 (the index there points here). New mechanism notes for this area go on this page, not in `CLAUDE.md`. A code comment that cites a `CLAUDE.md` section by name means a section now on one of these pages: `grep -rn '<name>' docs/internals/`.

### Common Issues

- **Text wrapping/clipping**: Check that layout measurement and paint use the same font stack
- **Elements stacking wrong**: Check the `display` property. `div` and other block elements default to `display: block` (per the UA stylesheet in `crates/rinch-dom/src/dom_impl/mod.rs`), so flex properties like `align-items` and `justify-content` do nothing until you set `display: flex` explicitly
- **`justify-items` / `justify-self` (and `place-items`' inline half) act in a grid and in block layout.** A flex container ignores them, as Chrome does. In a block container they place a block-level box (an auto width then shrinks to fit, and auto margins win over them, so `margin: 0 auto` still centres; #1985); floats, inline-level boxes and (still, #2541) absolute boxes are not moved. Read since #1511 (before, `ComputedStyle` carried neither, so `place-items: center` centred a grid item vertically only). `left`/`right` are physical: `start`/`end` under `direction: ltr`, the other way round under `rtl` (#1995). `safe` is honoured on both axes (#1987); a bare `legacy` is not inherited and `anchor-center` is dropped by Stylo's parser (#1987). Pins: `crates/rinch-dom/tests/justify_items_1511_tests.rs`, `crates/rinch-dom/tests/justify_direction_1995_tests.rs`.
- **`direction: rtl` reaches layout** (#1995): a grid's columns, a flex row and a block container's block-level children start at the right, and `justify-content: left/right` and `start/end` are told apart from `flex-start/flex-end` (a reversed flex container). Inline-blocks in an rtl line run right to left (#2542, parley fork item 7). An inline element's own `direction` reorders its content only through its `unicode-bidi` (`embed`, `isolate`, `bidi-override`, `isolate-override`, `plaintext`), as in Chrome (#2588); `normal`, the initial value, leaves the order to the paragraph. A paragraph's base direction is its block's `direction` whatever its first letter (#2594), or its text's under `unicode-bidi: plaintext`. The `dir` attribute is HTML's UA rules (`dom_impl::load_ua_stylesheet`): `dir=rtl`/`ltr` sets `direction` and isolates, `<bdi>`/`<output>` isolate, `<bdo>` overrides, and `dir=auto` (and a `<bdi>` without `dir`) is `plaintext`, rinch's stand-in for a direction taken from the content (Chrome's computed value is `isolate`). HTML's `isolate` on `div`, `p` and the other block elements is left out (it shows only on one made `display: inline`). **Not inside an rtl scroll container**: Chrome scrolls one from its right edge (`scrollLeft` runs negative, the overflow to its left is scrollable), rinch's scroll offsets and scrollable overflow start at the left edge, so everything an rtl scroller holds is laid out left to right, as before #1995, and its overflow stays reachable (`RinchDocument::lays_out_rtl`; Chrome's model is #2546). The root scroller (the viewport, and `<body>` when its `overflow` is propagated) is exempt: an `<html dir=rtl>` page keeps its rtl layout, and **its own horizontal overflow, laid out to the left, cannot be scrolled to until #2546**. Pins: `crates/rinch-dom/tests/rtl_scroll_container_tests.rs`.
- **A grid or flex container's own text** (#2411, #2443). Each run of a block-level grid's child text is an anonymous grid item (CSS Grid 1 §6.1), minted by `create_anonymous_block_boxes` (`ifc.rs`, `is_grid_container`) whether or not the grid also holds element children, so it is broken at its track's width; the grid itself is never an IFC root. A run of nothing but white space (spaces, tabs, newlines, under any `white-space`) is not rendered in a grid or a flex container: in a block-level grid its anonymous box is minted `display: none`; in a flex, `inline-flex` or `inline-grid`, whose text children stay Taffy text leaves, `hide_blank_text_items` sets the leaf's `display: none`. So indentation between tags takes no grid cell, no `gap` and no share of `justify-content`'s free space, as in Chrome. An edit of a text node into or out of white space seeds the structural pass (`set_text_content`), which is what re-decides it. A table is a grid in rinch and keeps its own blank-run handling (`table_layout::hide_blank_runs`).
- **Components sitting side by side where you expected a column**: `display: inline-flex` is **inline-level** (#595) — an *atomic inline*, like `inline-block`: it joins the line around it and shrink-wraps, and only its inside is a flex container. `Button`, `Badge`, `Checkbox`, `Switch`, `Avatar`, `ActionIcon`, `CloseButton`, `Loader`, `Pagination` and `Center` all declare it, so two of them in a plain `<div>` share a line, exactly as in a browser and as on rinch-web. Put them in a `Stack` (or any `display: flex` parent) to stack them — CSS blockifies a flex item, so the `inline-flex` is `flex` there and nothing about this applies. That includes an item behind any number of `display: contents` wrappers — every `for` row, `if` branch and component site `rsx!` emits — because blockification reads the **layout** parent, the nearest ancestor that is not `display: contents` (#998; rinch passed the DOM parent until then, so a wrapped `span` in a `Group` stayed `inline`). `display: inline-grid` is inline-level too, and has been since #607 — an atomic inline whose *inside* is a grid container rather than a flex one. `display: inline-block` is the third, and its **inside is a block container** (#592): its children stack, its inline runs get anonymous block boxes, and its own `font-size`/`font-weight`/`line-height` size its box. It laid its children out in a row until #592, because the Taffy container it built was a flex one
- **A bare `<select>` got a grey border and grew a few pixels** (#1098): the UA sheet now gives it Chrome 153's values — `padding: 0`, `1px solid rgb(118, 118, 118)`, no `min-width` (it had a 60px floor Chrome does not), and `line-height: normal !important`, so a declared line-height does not move it, as in Chrome. Its size is the label's: `border + padding + ceil(widest option label) + 20` wide (a 4px label inset and a 16px arrow box, kept *inside* any author padding — `select::SELECT_LABEL_INSET` / `SELECT_ARROW_BOX`) and `border + padding + one line + 2` tall, answered as its **content size** by a Taffy measure (`NodeContext::FormControl`, the one a text input carries; the select is a hollow root like a `<textarea>`, so its `<option>`s are detached from Taffy), so the author's `width`, `min-*` and `max-*` apply to it as to any box's (#1129): `max-width: 30px` is 30, `min-width: 50%` half the container, and `display: block` keeps the label width rather than filling, as in Chrome 155. Its `overflow` computes `clip` whatever the author says (UA `!important`, Chrome's value), so as a flex or grid item it does not shrink below its label unless given `min-width: 0`. At its default (inline-block) display its percentage `min-height` does not resolve as Chrome's yet, as for any atomic inline (#1738); its percentage `max-width` does since #2140 (it was 40 for Chrome's 50). It used to be `8px` tall — its vertical padding alone — with the label painted over its own bounds. The label is shaped for the measure by the same builder paint draws it with (`select::select_label_layout`, the #320 rule), and the width is cached on the node against the labels and the font (`shape_select_label` counts the shapes). An option's label is its text with ASCII whitespace stripped and collapsed, or a non-empty `label` attribute verbatim (spaces kept; a tab or newline drawn as a space, a CR or form feed as nothing), set in the select's `letter-spacing`, `word-spacing` and `text-transform` (an option's own do not reach it), and on the same face it gives Chrome 155's width to the pixel (#1130, `select_label_text_1130_tests.rs`). A height is 1.2em-based where Chrome's `normal` is the face's rounded ascent + descent, so within a pixel. An edit anywhere inside an option — a reactive `option { {|| x} }`'s text sits in a `display: contents` span — a write or removal of an option's `label` attribute, `set_inner_html` on an option (to `""` included) and an option moved to another select (both selects) re-size the select (#1128: `note_select_content_changed` walks up through any element to the `<option>`, and returns at once in a document that has never created one, `NodeTree::option_elements`). An option inside an `<optgroup>` is measured unindented, where Chrome 155 indents it (a 160px select is 178 there, #1736). The native **popup** is `max(select width, widest row + 30)` wide, at most the viewport's width, its rows set at 14px in the body's family and weight with the select's `text-transform` and no letter- or word-spacing, `white-space: pre` (Chrome 155's popup rows take the transform and neither spacing; `select_widget.rs`), measured by the same builder, so it is never narrower than the control and its rows fit — unless an author rule gives the rows another font than `<body>`'s. It opens at the select's left edge when it fits there, else ends where the select ends, kept on screen (Chrome 155's placement, #1132); Chrome's rows are in the select's font, rinch's in the body's at 14px. Chrome also gives a bare select its **own font** (13.33px Arial); rinch's inherits, so an unstyled one is still sized from the page's font. The `Select` component is a styled `<div>` and is untouched
- **A heading suddenly got bigger and bold**: since #627 the UA stylesheet gives `<h1>`–`<h6>` the browser's typography (`2em`…`0.67em`, `font-weight: bold`, `em` block margins) and `<th>` `font-weight: bold` plus a centring, so a bare heading renders as a heading on desktop the way it always did on rinch-web. They are cascade rules, so any author `font-size`/`font-weight`/`margin` still wins — which is why `Title`, `Modal`, `Drawer` and the editor's own stylesheet are unmoved. **The `<th>` centring is conditional and is spelled `text-align: -moz-center-or-inherit`, not `center`** — the HTML Standard's rule matches only a `th` "whose parent node's computed `text-align` is its initial value", so a header cell under an alignment its parent declares inherits that instead (measured in Chrome 150: `right` under a `text-align: right` ancestor). Stylo carries that value for exactly this rule and parses it for any **non-author** origin, so an app stylesheet cannot use it — the declaration is dropped there
- **A `<strong>` or `<b>` in a bold heading got heavier, or one in light text got lighter**: the UA sheet gives them `font-weight: bolder`, the HTML Standard's rule and Chrome's, not `bold`. So the weight is one step past the parent's (CSS Fonts' table: under 350 it is 400, under 550 it is 700, under 900 it is 900): 900 inside a bold `<h1>` or `<th>`, 400 under a 300 parent, and 700 under a normal one as before. Where the family has a face past its bold, the text takes it, as in Chrome: on a host whose fontconfig lists Arial Black in the Arial family, a `<strong>` in an Arial heading is Arial Black, which is wider and wraps sooner (a Postrinch mail's heading took three lines in Chrome and two in rinch). Until this change it was `bold`, 700 everywhere. An author `font-weight` still wins. Pins: `crates/rinch-dom/tests/ua_strong_bolder_tests.rs`.
- **A `<p>`, list or `<pre>` suddenly has space around it, or an `<hr>` appeared**: #674 finished the UA-stylesheet audit #627 started. `p`, `blockquote`, `figure`, `ul`, `ol`, `menu`, `dir` and `pre` now carry the browser's `margin-block: 1em`; `blockquote`/`figure` also `margin-inline: 40px` and `dd` `margin-inline-start: 40px`; a list nested in a list carries **none**, spelled `:is(ul, ol, menu, dir) :is(…)` as Chrome spells it (a *descendant* combinator — a `<ul>` under an `<li>` counts; `:is()` verified to match in this Stylo build, unlike `:has()`). `menu` and `dir` were in **no** rinch UA rule at all and so were `display: inline`; Chrome gives both exactly `ul`'s treatment, `padding-left: 40px` included. `<pre>` gets `white-space: pre`, so it finally preserves its newlines. `code`/`kbd`/`samp`/`pre` get `font-family: monospace` from the **UA sheet** rather than only from the theme. `small`/`sub`/`sup` get `font-size: smaller` (Chrome's 1.2 divisor — 13.3333px from a 16px parent, and it compounds). And `<hr>`, which rendered **nothing** before because the sheet's own `* { border-width: 0 }` reset applied to it, now carries `color: gray; border: 1px inset; margin-block: 0.5em; margin-inline: auto; height: 0; overflow: hidden` — a 2px grey rule. Every value measured in Chrome 150; all cascade rules, so any author declaration wins, which is why `Divider`, `List`, `Blockquote`, `Breadcrumbs`, `Tree` and `Image` are unmoved (they all declare `margin: 0`) — `Code` had to be given one. **The editor has one exception**: its stylesheet declares `margin`, `font-family` and `white-space` for every tag it renders but no `font-size` for `sub`/`sup`, so editor subscripts and superscripts now take `smaller` — correct, and what rinch-web always did, pinned by `the_editors_sub_and_sup_do_take_the_new_smaller_rule`. **Three consequences worth knowing.** The `<hr>` border is `currentcolor` over a UA `color: gray`, so `<hr style="color: red">` gives a red rule. A bare `<hr>` in a `Stack` collapses to a 2px dot and centres, because auto cross-axis margins suppress a flex item's stretch — that is what a browser does too (measured); use `Divider`, or `width: 100%`. And rinch does **not** reproduce Chrome's monospace font-*size* quirk (13px for a `medium` monospace element), so `<code>` keeps the inherited size. `vertical-align: sub`/`super` on `<sub>`/`<sup>` is done now (#724): `sub { vertical-align: sub }` / `sup { vertical-align: super }` are two more rules in this sheet, and `ComputedStyle::vertical_align` plus `ifc::vertical_align_shift_px` (`crates/rinch-dom/src/ifc.rs`) give an inline text run its shift. Since #1357 it is a parley `VerticalAlign` on the span (`ifc::span_vertical_align`), so the line box grows to hold the shifted span as Chrome's does, nested shifts add up, and the offset is rounded to whole pixels like every parley baseline. The `sub`/`super` ratios are calibrated against one measured point (Chrome 153, the bundled Inter, a 16px parent — see the field's own doc for the numbers and why they drift at other sizes); `<length>`/`<percentage>` are exact. `top`/`text-top`/`middle`/`bottom`/`text-bottom` on a text span are parley's own keywords too (#1357, as on an atomic inline); such a span's `InlineVerticalAlignSpan::from_layout` makes the caret, glyph bounds and background read where parley put the glyph run's baseline (`InlineLayout::layout_baseline_shift`), since it depends on the line. A split inline's (#513) keyword is still `baseline`. `display: list-item` (#725) is now partly done. `DisplayValue::ListItem` exists (`li { display: list-item }` in the UA sheet) for the block-outside, flow-inside forms only — `display: inline list-item` stays `Inline`, as in Chrome 153 — and its box lays out as a `block` one does: `taffy::Display::Block`, and `DisplayMode::Block`; a new layout site that asks for `DisplayValue::Block` must ask for `ListItem` too (pinned by `list_item_layout_and_nesting_725_tests`). The UA sheet's marker defaults are Chrome's own html.css rules — `ul, menu, dir` disc, `ol` decimal, `:is(dir, menu, ol, ul) :is(dir, menu, ul)` circle and three levels square — so an `ol` counts as a nesting level (`ol > li > ul` is circle, `ul ol ul` square; measured in Chrome 153). `resolve_list_marker` generates the marker, as a span at the start of the item, only for an `<li>` whose parent is a `<ul>`/`<ol>`, whose computed `display` is `list-item` (Stylo's `is_list_item()`, not `DisplayValue`), whose `list-style-type` is not `none`, and which has **no pseudo-element child** — any `::before` or `::after` suppresses it (Chrome draws both; a `menu`/`dir` item and a non-`li` `display: list-item` get none — #1370). So an author override off `list-item` — `rinch-components`' `List` items with an icon, or every item of a `center`ed `List`, at `display: flex` — draws no marker (it drew a bullet beside the icon before). Its glyph follows the item's own `list-style-type` for `disc`/`circle`/`square` (`•`/`◦`/`▪`) and `decimal` (`N. ` via `compute_list_item_counters`, `<ol start>`/`<li value>` included); any other keyword still gets the old tag-based bullet/number rather than none (alphabetic/roman types are out of scope, and roman is not in Stylo's servo-build keyword set). **The marker is an outside box since #1356** (`crates/rinch-dom/src/list_marker.rs`, whose module doc has the rules). `resolve_list_marker` reads `list-style-position` and generates the marker as a `<rinch-marker>` element (not a `<span>`, so no rule for the item's children matches it, as none matches a `::marker`) stamped `rinch-list-marker="outside"` or `"inside"`. The UA sheet keys `!important` resets on that attribute: box, `position: static`, the item's font, colour and visibility (`inherit`), and `opacity: 1` and no background, outline, shadow or filter, so a universal rule (`#t > *`) or a `rinch-marker` rule changes nothing it resets (a property outside the list, such as `text-decoration`, does still reach it: answering `false` from `has_local_name` for it was tried in review round 2 of #2271, and Stylo still applied a `rinch-marker` rule, so it was not kept). `text_content` of an `<li>` includes the marker's text, as it includes every generated box (#1629); `query_selector`, structural selectors and copy skip it. An `outside` one is a static block for style, paint, clipping and stacking: it paints in its item's flow and is clipped by whatever clips the item, the item's own `overflow: hidden` included (review of #2271; it was `position: absolute` at first, and escaped a scroller's clip and painted in the positioned layer). Only its **Taffy** box is out of flow: `taffy_style_from_computed` writes `taffy::Position::Absolute` for it, and `Node::is_out_of_flow` answers true so the inline formatting context keeps it out of the item's lines. It is marked `Node::outside_marker`; the read-back keeps the `x`/`y` it has, so an unmoved marker is not repainted, and `place_static_after_lines` skips it. `RinchDocument::place_list_markers`, run by `resolve_layout` after the layout and `align_table_cells` whenever the layout epoch moved, writes its place. Its baseline goes on the item's first line box, searched through in-flow block descendants in Taffy order (skipping out-of-flow boxes, floats and blocks with no line). A table answers its first cell's content-box bottom. A flex or grid item's own text is placed by the marker's font metrics, because its shaped lines are not kept in every state. It hangs from the item's **border-box** edge (Chrome 156 ignores the item's own padding and border there). A symbol is centred by Blink's `ascent * 2 / 3 + 8` rule. **It places only markers that can have moved**: the ones generated since the last pass (`NodeTree::outside_markers`), and those of items above a box in `NodeTree::marker_moves`. The read-back records a box there when its layout changed (the box itself when it resized, its parent up when it only moved), and `build_inline_layout` records an IFC root that got new lines. Inline content is skipped. The walk up is stamped (`Node::marker_walk`), and the cost is `list_markers_placed`. A new site that changes a box's layout or an IFC's lines without `note_marker_move` leaves markers where they were. An item with no line box gets `Node::marker_line_floor`, a minimum content height that `taffy_style_from_computed` applies while the item still has its marker (`apply_marker_line_floor`), and the layout is resolved once more when a floor appears or goes. A new site that builds an `<li>`'s Taffy style without `taffy_style_from_computed` drops the floor and the marker's out-of-flow Taffy position. Text: a symbol alone (`inside`: the glyph, an en space and a four-per-em space, Chrome's shape plus its 1em margin with the bundled Inter; text, not an `inline-block`, because parley gives an inline box at the start of a paragraph the left-to-right bidi level), and a number `N. ` with an ordinary space. Known differences: no tabular digits on a number; an `inside` glyph sits about 0.12em right of Chrome's shape; a marker line taller than the line it sits on does not push the content down; and a later in-flow block's background paints over the marker, as over any earlier inline content, because rinch paints CSS 2.1 Appendix E steps 4-7 in tree order (#2276). The editor's stylesheet no longer hangs the span itself; it still hangs its task-list checkbox `::before` against the item's left edge — as flex items beside the item's paragraph, they put a long paragraph on a line of its own, #1246.


- **A raw `<input>` or `<textarea>` grew a grey border, padding and a smaller font**: #1194 gave the text controls Chrome 153's UA defaults (measured under a parent that declares the opposite of each). A text-state `<input>` (no `type`, `text`, `search`, `email`, `password`, `number`, an unknown type) has `padding: 1px 2px; border: 2px inset rgb(118, 118, 118)` (drawn solid, as every `inset` is); a `<textarea>` `padding: 2px; border: 1px solid` of the same grey; the date/time family `padding: 0 0 0 1px` (the inline start only) with the input border; `checkbox`, `radio`, `range`, `file`, `image`, `hidden`, the button types and `color` none (Chrome gives the button types `1px 6px` and a `2px outset` border and `color` `1px 2px` and a `1px solid` one — not modelled here, Refs #1266). Both controls take `font: normal 400 13.3333px/normal` and reset `letter-spacing`, `word-spacing`, `text-transform`, `text-indent` and `text-align` — Arial on an `<input>`, monospace on a `<textarea>` and the date/time inputs — and a `<textarea>` also `white-space: pre-wrap; overflow-wrap: break-word` (an `<input>` keeps inheriting both). Since #1177 a control is `size`/`cols` average characters of **its own** font wide, so this moves widths too. Overflow: an `<input>` other than a checkbox, radio or range is `overflow: clip !important` (Chrome's spelling — an author `overflow: auto` still computes `clip`); a `<textarea>` is `overflow: auto`, and an author `visible` on either axis computes `auto` (Chrome's post-cascade adjustment, made in `apply_stylo_styles_to_taffy`), so a raw textarea shrinks as a flex item (to 100px in a 100px row); an author `clip` or `hidden` is kept. rinch still never lays out or scrolls a textarea's text, so it paints no bar and takes no wheel (Refs #1266). All but the input `clip` are cascade rules, so `TextInput`, `Textarea`, `NumberInput`, `PasswordInput` and `ColorInput`, which declare their own font, padding and border, are unmoved, and the theme's `button, input, select, textarea { font-family: inherit }` still wins the family (the 13.3333px size stays, as in Chrome under the same sheet). Not done: `color: FieldText` / `background-color: Field` (the theme's `color: inherit` is deliberate), and the font reset on `<button>` and `<select>`. Pins: `crates/rinch-dom/tests/ua_form_control_defaults_tests.rs`.
- **An `<input>`'s text moved right by its border width, or a long value is cut off at the field's edge**: since #1721 a single-line `<input>` is laid out as **one unwrapped line** (it used to wrap at its width and paint the extra lines centred over whatever lay above and below it), starting at its **content box** — border plus padding (`form_control::text_column`; it started at its left padding, over the border) — clipped there whenever the line overflows or is scrolled, and scrolled horizontally to keep the caret in view, as Chrome 155 does: a caret move past an edge (arrows, Home/End, typing, a press) scrolls by the least that shows it, a focus whose caret is out of view centres it, a blur scrolls back to 0, and the scroll is clamped to the text's width plus the 1.5px caret (`form_control::input_scroll_x`, state in `Node::input_scroll_x`, `NaN` while unfocused). Every geometry consumer asks that one function — paint (text, selection, caret, IME underline, placeholder, password bullets), the press → offset map and the caret rect (`RinchApp::input_text_layout`, `form_control::painted_caret_rect`, so `NodeHandle::caret_rect`), the IME cursor area (the caret of the **displayed** text, so the end of an IME composition: `form_control::input_displayed_caret_rect`, `RinchApp::input_caret_area`) and the MCP `get_caret_position` and `get_glyph_bounds` — and the shell reveals eagerly at every caret sync and preedit write, so keys between two frames scroll as they would a frame apart (`keys_between_reads_reveal_at_each_move`). The displayed line is shaped once per change of its text, caret or font and kept on the node (`form_control::displayed_metrics`, counter `shape_input_scroll`), so paint, the per-pass IME poll and a click at an unchanged state shape nothing for the scroll. A press-drag past the edge does not autoscroll: rinch has no drag-select in a form control. Pins: `crates/rinch/src/app/input_horizontal_scroll_1721_tests.rs`.
- **A `<textarea>`'s text moved by its border width, or its text scrolls** (#827): a textarea's text column is its **content box** too (it started at its left padding on both sides, over the border, and at its top padding), its text wraps at that width, and a textarea is a **scroll container** (`overflow` computes `auto`) whose content extent is its text: `paint::scrollbar::content_extents` reads the text height `form_control::textarea_scroll_extent` keeps on the node (shaped by `form_control::displayed_metrics` — at every layout's `clamp_scroll_offsets`, at the first resolve after its value changed, at paint and at each caret move, only when its text, caret, wrap width or font changed; the focused field keeps its layout in `Node::input_text_layout`, so a caret move reads the caret off it and shapes nothing). A value write runs no layout, so `NodeTree::push_dirty` queues a textarea whose `value` or text child was written (`NodeTree::textarea_extent_dirty`), and a resolve that skips layout refreshes its extent and clamps its scroll (`RinchDocument::refresh_value_changed_textareas`, `onscroll` queued like a clamp): a value that fits scrolls back to 0 and `scroll_height` is the new value's right after the resolve, as in Chrome. So the wheel, the overlay scrollbar, `scroll_top`/`scroll_height` and layout's clamp all work on it as on any scroller, and its text is painted at `border + padding - scroll_offset.1`, clipped to its padding box whenever it overflows or is scrolled. A caret move scrolls it by the least that shows the caret's line in the field's **padding box**, its scrollport, as Chrome does (`form_control::reveal_caret`, from the caret sync and the preedit write, queued for `onscroll` like a clamp) — Ctrl+End puts the last line at the padding box's bottom with the bottom padding scrolled out (Chrome 156: 141 of a 146 range), Ctrl+Home from below scrolls to the top padding's height (Chrome: 5), not 0, a new line typed there scrolls one line, a move inside the view scrolls nothing, so a wheel-scrolled field stays put — and a blur keeps the scroll, as Chrome 155 keeps `scrollTop`. No scrollbar gutter is reserved (rinch's bars are overlays). **One builder, one origin:** every consumer of a field's text geometry — paint, the press map and the caret/glyph rects (`RinchApp::input_text_layout`), `form_control::painted_caret_rect` (`NodeHandle::caret_rect`, MCP `get_caret_position`), the IME area (`form_control::input_displayed_caret_rect`, now for a textarea too — it answered the field's top at full height) and the scroll metrics — shapes with `form_control::field_text_layout` and places the layout at `form_control::field_text_origin` through `form_control::field_scroll`. A single-line field's press map used to centre with `max(padding_top, (h − text_h)/2)` while paint used `(h − text_h)/2`; they now agree. The builder's configuration is still font size, family and weight: moving it to `ComputedStyle::build_parley_layout` (#320) is a change to `field_text_layout` alone. Pins: `crates/rinch/src/app/textarea_scroll_827_tests.rs`.
- **A table lays out differently from a browser**: `crates/rinch-dom/src/table_layout.rs` is the table layout, and its module docs are the design. A table is a Taffy grid; row groups and rows compute `DisplayValue::Contents` and generate **no box**, so their `layout` is all zeros and a query of a `<tr>`'s rectangle answers nothing (read a cell's). `resolve_tables` rebuilds a table owed one (`NodeTree::tables_owed`: any part restyled, a child inserted, moved or removed), placing each cell by the HTML forming-a-table algorithm, and every rebuild of a Taffy style from `computed_style` goes through `taffy_style_from_computed`, which applies the placement (`apply_table_style`); a new site that calls `to_taffy_style` directly loses it. A cell's `computed_style` is not purely the cascade's: a collapsing table writes the winning borders there and `vertical-align` adds to `padding_top` after layout (`align_table_cells`), so consumers of text origin and border need no table knowledge. That padding moves everything the cell's own lines place — its text, and the atomic inlines in them, whose boxes are relative to its content box — so only the children Taffy places take the shift on their `y`, as the difference from the offset they carry (`TableCell::kids_shift`; #2144: an atomic inline took it once per layout on top of the padding, drawn at 2x, 3x, ... the offset). A restyle clears both, which is why any table part's cascade owes the table, and queues the cell to be aligned again even when no compute runs (a colour change used to drop the cell's content to the top). A table with a width of its own asks each cell its max-content width, size-only and only once the cell changed (`TableCell::max_content`, #2141); it weighed the columns before #2306, and nothing reads it now. Which cells and tables changed is noted at the start of every layout that computes (`note_changed_tables`), before an atomic inline's own compute or a layout in which the table has no width clears Taffy's dirty flags; a table whose columns moved has its atomic-inline ancestors laid out again before the root compute (#2156); a spanning cell or a caption keeps the detached layout of the whole table, a second root compute. A cell's leftover height for `vertical-align` is measured from its content, its lines and the bottom of its floats' margin boxes (a cell is a block formatting context root): with its lines alone, a float taller than the cell's text was moved down by half the difference (#2326). A `table-layout: fixed` table whose `width` is a percentage asks for all the room it is offered: its max-content width is 1,000,000 (Blink's `kTableMaxInlineSize`, the Taffy fork's `fill_max_content`, set in `apply_table_style`), so an auto table cell, a block-hosted table's column, a float or an inline-block around it fills its room and the percentage resolves against that, as in Chrome (#2322: an email's `width:75%` fixed table in a `<th style="display:block;width:100%">` column was a quarter of Chrome's width). An auto-layout table, or a fixed one with no width, is content-sized as before; a mixed `calc()` width does not fill (Chrome fills). Known differences: `baseline` aligns as `top`; a collapsed border sits whole on one side of the grid line, where a browser centres it; an image on a row or row group is not painted, only a colour; a caption is inside the table's box, so the table's own background and border reach it, and it sits inside the table's border (Chrome: outside, #2394; it is outside the padding and the outer spacing since #2350); and rinch is always in no-quirks mode, so a mail with no doctype differs from Chrome's quirks rendering (`font-size` and `text-align` reset at `<table>`). A cell's `max-width` caps what the cell asks of its column and nothing else (#2264; Blink's `CreateCellInlineConstraint` caps the cell's min-content, max-content and CSS `width` contributions, and `SetupTableCellConstraintSpaceBuilder` lays the cell out at its columns' width): the cell keeps its `max_size` in Taffy, which caps the contributions the grid measures, `declared_track` caps a cell's `width` at a length `max-width` (in either table layout), and every cell's Taffy style carries `stretch_past_max_width` (the Taffy fork's commit 9), so the grid stretches the cell to its column past the cap and measures its row height at that width. No condition on the table: a capped cell in a 400px table, a `min-width: 400px` table, or a column another row or a colspan widened fills the column, and alone in an auto table it is its `max-width`. Only a `display: table-cell` box: a `<td style="display: block">` (or `flex`), email's column-stacking pattern, is a block in an anonymous cell and its `max-width` clamps it (Chrome: 90 in a 400px table). A cell's `min-width` wins over its `max-width` in its `width` contribution, as everywhere in CSS. Email writes `width:540px; max-width:540px` on the one cell of a 665px table, and the cell is 665 in Chrome. The flag is written on every sync from the part alone, so a restyle cannot strand it, and a node that stops being a cell gets a fresh Taffy style without it. Pins: `crates/rinch-dom/tests/table_cell_max_width_2264_tests.rs`. A table whose declared `width` is under its columns' minimum widens to it, as Chrome does (#2266; automatic layout only, a `table-layout: fixed` table keeps its width): its Taffy style sets `item_is_table`, so its block parent leaves it to resolve its own width, and the fork's grid widens to its tracks (item 12). An automatic-layout table shares its width as Chrome does (#2280, #2306, #2281): its grid sets the Taffy fork's `proportional_column_sizing` (items 10 and 12), so between Blink's guesses each column that differs between them grows from one to the next by the same fraction of its difference — a table narrower than its declared columns gives each its min-content plus the same fraction of its declared width (padding included) minus min-content, a column with a `width` reaches it before the `auto` columns grow, and they then grow from min-content towards max-content — and past every column's max-content the excess goes to the `auto` columns in proportion to their max-content (in equal shares when they are all empty, an email's filler cell beside its logo: 108 / 280 in Chrome), or to the declared ones in proportion to their widths, then to the percentage ones. A colspan cell's min-content and max-content beyond its columns' go to them in proportion to their max-content. A grid's equal shares made a narrow column as wide as a long one, and a table with a width shared it in proportion to the declared or max-content widths (Postrinch mail 033, 20px taller than Chrome). Pins: `crates/rinch-dom/tests/table_auto_column_shares_2280_tests.rs`, `crates/rinch-dom/tests/table_width_distribution_2306_tests.rs`. Still different: a percentage resolves against the table's width less its outer spacing, where Chrome leaves out every spacing (#2333: 88 where Chrome gives 84); percentages past 100% are not capped (#2334); a percentage column in an auto table is an `auto` track (#2284); an auto table's `min-width` above its max-content, and a column only colspans cover (#2285). A replaced element (an `<img>`, …) whose `width` or `max-width` is a percentage is *compressible* (css-sizing-3 §5.2.2, `replaced::is_compressible`): its min-content contribution is computed with those percentages resolved against zero, so it is its length `min-width` or nothing, plus its padding and border. Asked for its min-content width it answers 0 (`replaced::contribution`, at the four replaced measure sites in `layout_engine.rs` and `ifc.rs`), so `<td width=390><img width=100%>` keeps its declared column and the picture scales into it, as in Chrome; before, the picture's natural width widened the column. A **length** `width` beside the percentage `max-width` (`width: 800px; max-width: 100%`, email's picture markup) does not hold at min-content either: the Taffy fork's block algorithm leaves the width unknown there (item 21 in `dependencies.md`) and the leaf is computed with the percentages resolved against zero (`replaced::min_content_style`). It used to make the column 800 wide: Postrinch mail 033's `max-width: 640px` card was 872 wide and 1,120px taller than in Chrome. An **inline** picture is lined up at its compressed width in a min-content measure of its line (`replaced::compressed_inline_min_content`, in `AtomicContributions::size`); it was lined up at its natural width in every measure, so an 88px logo with `max-width: 100%` widened its `width: 45pt` cell to 88 (#2398; Chrome 156: 60). Pins: `crates/rinch-dom/tests/compressible_replaced_min_content_tests.rs`. A `calc()` holding a percentage is not detected, and a float around a compressible picture is still sized from the picture's length `width` (a `float: left` holding a `width: 800px; max-width: 100%` picture in 696px is 800 wide; Chrome 696). A percentage `height`, `min-height` or `max-height` inside a cell with no fixed height behaves as `auto` (CSS 2.1 §10.5, `unresolve_heights_in_auto_cell`). A row whose children are all blocks (email's `<th style="display:block">` phone columns) puts each in a row of its own in the first column. A block in a row of real cells (email's `<td width=15 style="display:block">` spacers) keeps a column of its own. Either way the block stands for an anonymous cell, whose width is `auto`: its `width` (attribute or CSS) is the block's own, kept in Taffy with its margins, and does not declare the column, so a wide table's free width goes to that column by the block's width as a weight, as in Chrome, and not to the declared columns (#2288: a header row of icon cells, `width=32`, after a block spacer was drawn at the left, Chrome at the right; pins: `crates/rinch-dom/tests/table_block_cell_2288_tests.rs`). Its side margins are part of what it asks of the column, and the `<td>`'s UA `vertical-align: middle` does not move its content (the anonymous cell's is `baseline`; `align_table_cell` aligns only `display: table-cell` boxes). Such a block is as tall as its content (`align-self: start`), as in Chrome: a 10px block in a `height: 40px` row is 10 tall and the next row starts at 40 (#2312; it was stretched to the row). Its anonymous cell's `vertical-align` is `baseline`, which rinch aligns as `top`, so it sits at the row's top; that is Chrome's answer only when no cell of the row is baseline-aligned (#2359: beside a `vertical-align: baseline` cell with `padding-top: 20px`, Chrome lowers it to y=20). A row's length `height` (its style, or the `height` attribute, which maps to it; `0` included) is the least its grid track is (`TableBox::row_heights`, the module docs' *Row heights*): `minmax(<height>, auto)`, so a row of empty cells is that tall and a taller cell grows it. The rows are sized by the Taffy fork's `table_rows` (item 15 in `dependencies.md`), Blink's row algorithm, not by the grid's: a row with a `height`, or holding a span-1 cell with one, is *constrained*; a taller table gives its extra height to its body sections (not a `thead` or `tfoot`) in proportion to their heights as they were before any rowspan grew their rows (Blink records a section's height before its rowspan step), and each section to its unconstrained rows that hold something, in proportion to their heights (a 200px table with a 30px row and auto rows of 20 and 40: 30, 56.66, 113.34), else to its empty rows, else to every row by its height (rows of 30 and 20 in a 100px table: 60 and 40); a `rowspan` cell taller than its rows grows them the same way, except that a row where another spanning cell starts comes first and, when all are empty, the last takes it all (a 120px cell over rows of 30 and 20: 72 and 48); a caption takes none of a table's height (a 200px table with a 20px caption is 220 tall); and a table whose `height` is less than its rows grows to them, also when its parent imposes its height: a column flex item, a grid item stretched to a shorter track (it overflows the track, and the next track stays put) and an absolutely positioned table in a block, flex or grid container grow as in Chrome (#2358: they stayed at the height handed down; the fork's `resolves_own_height` on each child style). All five were #2312: the grid shared each of these equally, stretched the caption with the rows, and kept a short table at its `height`. Before, rows generated no box and their height reached nothing, so an email's `<tr height="32"><td></td></tr>` spacer was 0px. A percentage row height and a row group's `height` (Chrome gives it to its rows) size nothing. Still different: a percentage row height and row baselines, which the fork does not model. A caption is outside the table's padding and outer `border-spacing`, with no spacing between it and the rows or another caption (#2350; the module docs' *Captions*: the fork empties the gutters beside a caption row and the caption's margins take the padding back; its own percentage, `calc()` and `auto` margins are resolved against the table's width by the calc pass, except a percentage side margin in a content-sized table, which is zero); before, it sat inside the spacing, with one more spacing before the first row. Pins: `crates/rinch-dom/tests/table_caption_spacing_and_imposed_height_tests.rs`. A restyled row owes its table a rebuild already, as every table part does. A table with `border-collapse: collapse` has no padding (CSS 2.1 §17.6.2; `TableBox::collapse`), as in Chrome; a block standing for a table keeps its own. Pins: `crates/rinch-dom/tests/table_row_height_tests.rs` and `crates/rinch-dom/tests/table_row_heights_2312_tests.rs`. A declared column's limit is its width floored at its cells' min-content, and a table of declared columns shares its excess by those (#2288, #2306): `<td width=50>` holding a 100px box takes 250 of 400 beside `<td width=60>`, as in Chrome (182 before #2288), a `width=100%` picture in a `width=300` cell still weighs 300, and another cell's max-content in the column does not count (Chrome 156: `<td width=50>` over a cell of max-content 206, beside `<td width=60>`, shares 56:66). A block or inline-block whose in-flow children are all rows, row groups or cells, with no text (`display: block` or `inline-block` on a `<table>`, `display: inline-block` on a `<tr>`: email's centred rows of buttons and social icons), takes the table's part itself, standing for the anonymous table CSS would wrap them in (`note_table_host`, `is_host`): it keeps its own width (a block's, or an inline-block's shrink-to-fit or declared width) and its grid tracks pack at its start, so its cells stay side by side at their own widths (an inline-block one used to stack them, each as wide as the widest); it gives the part up when it is restyled or rebuilt and no longer qualifies (`unhost`, which also shows the blank runs the table hid); a child-list change or a text write on a plain block owes it a look, so a block that loses its last non-row child becomes one. A block that mixes table parts with other content is not a host (CSS wraps each run of parts in its own anonymous table; not modelled). A table cell whose parent box (seen through `display: contents`, rows and row groups) is an inline is laid out as the anonymous `inline-table` CSS wraps it in (CSS 2.1 §17.2.1; #2510, `table_layout::wrap_cell_in_inline_table`, run on the cell's new style as it is cascaded): the cell itself becomes an `inline-block`, as wide as its content, with the table's `vertical-align: baseline`; its own `vertical-align` is kept in `ComputedStyle::anonymous_inline_table` and says where the table's baseline is (`ifc::atomic_inline_baseline`: a baseline cell's first line, else, or with no line, its content-box bottom, as Chrome 157 puts a `vertical-align: middle` count's content bottom on its icon's bottom). The inherited `border-spacing` (2px under a `<table>` with no `cellspacing`; none under `border-collapse: collapse`) is the anonymous table's padding and the gap between its cells, so the cell has it above and below as margins (which its line lines up), and beside it as edge boxes the IFC pushes around its inline box, glued to it as an inline element's edges are: after it, and before it unless it follows another such cell (`table_layout::follows_inline_cell_in`, asked as the IFC is built). Not as side margins, because an atomic inline's side margins take no room on its line (#1405). Chrome 157: 2px under a `<table>` puts a mail's count 2px right and 2px down, the line 4px taller. A white-space text node right after such a cell is laid out as no text (`ifc::is_blank_after_inline_cell`): Chrome takes it into the anonymous table, so the space between two cells and the one before an element after a cell go, while text that starts with a space, and a space before a cell, keep it. A parent whose display crosses `inline` has its cells cascaded again (`inline_table_cells_under`; a display change recascades the children already, but not the cells under a row that did not change). Before, the cell was a block that split its inline and took a line of its own (a mail's notification count under its icon instead of beside it). Not modelled: consecutive cells are each their own box, so they are not stretched to one row's height (Chrome: a 4px-padded cell beside a 10px-padded one is 40 tall, as tall as the other; rinch's keeps its own height); a row's children that are not cells flow as inline content, where CSS wraps them in an anonymous cell; and a cell in a block that also holds other content keeps its block's width, where Chrome's anonymous table is as wide as the cell's content. Pins: `crates/rinch-dom/tests/inline_table_cell_tests.rs`. A cell whose height becomes or stops being a fixed length rewrites its children's Taffy styles (`note_cell_height`), since their percentage heights resolve by it. HTML's `align` on a div, cell, row or row group computes Stylo's `-moz-center`/`-moz-left`/`-moz-right` (`ComputedStyle::html_align`), which a table does not inherit, and also aligns the block boxes under it that have a `width`, a `max-width` or a table's width and no `auto` margin. That is done where Taffy's layout is read back (`html_align_dx`; asked only once some element has cascaded with one, `NodeTree::html_align_seen`, so a document without the attribute pays nothing per box — it cost the Perf benches 1.4–3.6% per layout before, batch PR #2224), as Chrome places the margin box: centred, `left = ml + max(0, free / 2)`; at the end, `max(ml, avail - width - mr)`; the box keeps its own margins in Taffy, so a relative offset or a transform still applies on top.
- **A box with padding or a border is bigger than its `width`/`height`**: `box-sizing` is read since #1278. Its initial value is `content-box`, so `width` and `height` size the content and padding and border go outside, as in a browser; before #1278 every rinch box was sized as `border-box` (Taffy's default) whatever its CSS said. rinch-theme sets `* { box-sizing: border-box }`, so a themed app is unchanged; unthemed content (an HTML email, a fixture) now matches Chrome. The UA sheet gives `border-box` to what Chrome's does: `table`, `select`, `button`, `meter`, `progress` and the button-like, checkbox, radio, colour and search `input`s. Where rinch writes a measured width back into a box's Taffy style (a keyword or shrink-to-fit width, `RinchDocument::resolve_root_width_keyword`; the clamp pass and `relayout_atomic_inline_at_its_width`; an absolute box between two insets or `width: stretch`, `out_of_flow.rs`), it converts the measured border-box width into the box's own sizing box (`ifc::sizing_box_width`), or the box grows by its padding, and again on every layout. An auto-width `<body>` is given `width: 100%` of `<html>` with `box-sizing: border-box` when it declares no height (`node::body_taffy_overrides`), so a padded body fills the viewport rather than overflowing it. Many oracle test files were measured in Chrome under `* { box-sizing: border-box }` to match rinch's old behaviour; they load that rule on the rinch side too.
- **Floats** (`float_wrap.rs` and `floats.rs`, module docs are the design): Taffy 0.14's `float_layout` places floats and clears. A paragraph's lines wrap around the floats beside it line by line, as a browser's do: its IFC root is a Taffy leaf, and rinch's Taffy fork hands a leaf the `BlockContext` it is laid out in (`compute_layout_with_block_measure`, see `dependencies.md`), from which `FloatBands::of_leaf` reads the room the floats leave at each height. The line breaker (`ifc::hang_pass`, which every paragraph beside a float goes through) gives each line that room with parley's per-line `line_x`/`line_max_advance` (`place_line_beside_floats`), checking the line's whole height; a line whose first piece does not fit is moved down to where the room changes (CSS 2.2 §9.5), and the gap counts in the root's height (`InlineLayout::content_height`). "Does not fit" is the line's content less the white space that hangs at its end (parley's `hanging_advance`) against the room, whatever ended the line (`ifc::line_overflows_room`): parley keeps a word too long for the room whole and ends the line `Regular` at the space after it, and a `Regular` end was taken to mean the line fit, so a long word or URL beside a float stayed beside it, overflowing (#2360: `Supercalifragilistic word` beside a 250x37 float in 300px, Chrome puts the line at 37). Two things the old rule hid had to be right for that: a line overlaps the band it starts in whatever its height (`FloatBands::room`; its `top + f32::EPSILON` was `top` at 20.0, so a line starting on a band's top got the whole width), and a band starting partway down a line leaves it less room than its trial break had, so `place_line_beside_floats` breaks the line again at that room before judging it (a 100x40 float mid-paragraph, stacked floats ending on line tops: review of #2374, `float_room_round3_tests.rs`). Not yet Chrome's (#2378): a word the line may break (`overflow-wrap: anywhere`, `word-break: break-all`) is moved below rather than broken beside the float, and `text-indent` is left out of the check. The room at a height is what every float there leaves: a line starts after the rightmost left float it overlaps, never in the gap a shorter float left when it ended (#2362). Taffy's float context lost the part of a float that reached below every segment placed so far (the fork's item 16), so left floats 100x30 then 100x50 gave a line at 40 the whole width, and a later float went into the gap. The line is first broken as CSS ends it (after the seams rebreak, which glues a `nowrap` run parley broke after each box) and moved again when that line overflows the room: `place_line_beside_floats`'s trial break is parley's and does not see the glue (#2331: `<float 100x31><span nowrap>` 603px of boxes stayed beside the float, overflowing; Chrome puts it at 31). A float the paragraph places at the start of a line counts as beside it, so a line it leaves too little room goes below it, in the measure as in the paint layout (#2331: a cell holding a 36px float and a 311px box was 38 tall, Chrome 58; the block was as tall as the line alone); one placed after content of the line's own does not move the line (`abc<float>def…` stays at the top, overflowing, as in Chrome). A float's out-of-flow box gives the CSS line no end of its own: `css_line` takes no break while the line holds nothing in flow, which made an empty line before a `nowrap` run. Lines past a float's bottom get the full width back, and the paragraph's box (and background) stays full width. The paint layout is broken around the bands the last measure saw (`NodeTree::ifc_float_bands`), and rebuilt when they change. parley's `Cluster::visual_offset` and `Cursor::geometry` (0.11.1, and 0.12 still) leave a line's start out, where its glyph runs, inline boxes, hit test and selection rectangles count it: rinch reads them through `float_wrap::cluster_x` / `caret_box`. A block-level image or form control beside a float still avoids it as a box (Taffy-only `contain: paint`, `sync_float_avoidance`), as CSS has a replaced element's border box do, and an anonymous box of nothing but the white space around a float between two blocks is hidden (`float_blank_runs`), as a browser collapses it. A float among inline content is out of flow (`InlineFlowRole::OutOfFlow`, as an absolute box is): it splits neither the run nor an inline element around it (`block_in_inline_tests::a_floated_child_of_an_inline_matches_its_wrapper_free_twin`, 20px as in Chrome), and stays a Taffy child of its IFC root, **before** the measure leaf (absolute children go after it, for their static position). Taffy sizes such a float and leaves it to the leaf to place (the fork's `PendingFloat`, asked of measure leaves only: `float_wrap::is_measure_leaf`). Where the float stands in the text is a box of no size (`ifc::FLOAT_BOX`, an edge box to every walker, `edge_box_owner` `None`) of kind `CustomOutOfFlow`, at which parley's breaker pauses: `hang_pass` places the float at its line's top when it fits beside what the line holds so far, else at the next line's top (CSS 2.2 §9.5.1), and narrows the line (`PlaceFloats`, `float_wrap::BlockFloats`). Every other loop over a breaker consumes such boxes (`skip_float_boxes`); parley's own `break_all_lines` is never run on a layout that holds one, or it yields the same box for ever. parley's `TreeBuilder` (0.11.1, and 0.12 still) gives a non-`InFlow` box the committed text length as its position without committing the text before it, so the replay commits it with an empty span first (`ifc::push_inline_box`). The paint layout is broken around the bands the measure recorded after placing its floats. Asked its intrinsic width, a paragraph holding floats is measured with them (the fork's `BlockContext::is_intrinsic`, item 14 in `dependencies.md`): it is laid out with no float placed, and each float's margin box is added to the line it stands in (`float_wrap::intrinsic_width_beside_floats`; a float that clears a side starts that side's sum again), so at max-content a line is as wide as its content and its floats, as Blink measures it (#2326). An auto table cell, float or inline-block holding `<float> text` is as wide as both; it was the wider of the two, and the text wrapped below the float. A block after a float does not share its line, in Chrome as here. At min-content each float is its own. A float sized from its content resolves its children's percentages against the width it took (the same fork item). A float holding wrapping content is as wide as its room (fit-content, `InlineLayout::fit_content_width`; see `positioning.md`, "The shrink-to-fit width"): it was as wide as its widest line (`float:right` holding a 431px paragraph in 300px was 277 at x 23, Chrome 300 at 0; #2330). Still different: a float inside a `nowrap` run after content (`<nowrap><ib><float><ib>`) lets the line break after it, where Chrome keeps the run on one line; and `display: flow-root` does not contain floats (it is laid out as a plain block). A float inside a flex or grid container does nothing, as in a browser.
- **A stylesheet rule that matches nothing**: desktop's **selector** surface is narrower than a browser's and every gap is silent — the rule parses, then matches nothing, with no warning. `#id` works as of **#675**: `TElement::id()` now hands Stylo a stored, interned `Atom` (`Node::id_atom`, written by `Node::write_attribute` / `erase_attribute`), where it returned a hard `None` before, so `SelectorMap::get_all_matching_rules` never consulted the id bucket and `has_id` — correct all along — never ran **for a rule whose rightmost compound carries the id**. An ancestor-side id (`#a > p`, bucketed by `p`) always worked, which is the asymmetry that hid it. An UPPERCASE attribute name — `<div ID="up">`, `[DATA-X]` — works as of **#688**: the store folds the name in HTML content and Stylo already hands `attr_matches` a lowercased selector name, so both ends meet. The `[attr=v i]` case-insensitive flag works too, since `attr_matches` delegates to the selectors crate's `AttrSelectorOperation::eval_str` — the evaluator Stylo's invalidation snapshots use, so an element and its snapshot cannot disagree (#682). A camelCase SVG type selector (`linearGradient { … }`) works as of **#683**: `is_html_element_in_html_document` answered a hardcoded `true` for every element, which made the selectors crate compare it against the selector's *lowercased* spelling (HTML's rule); it now answers `false` for an SVG content tag (`attr_name::is_svg_content_tag`, the predicate #688 already built for the sibling attribute-name question), so the author's exact spelling is kept. `:required` / `:optional` / `:read-only` / `:read-write` / `:placeholder-shown` / `:defined` / `:lang()` work as of **#681** — each narrower than the full CSS definition (see `Node::tag_supports_required` / `Node::tag_is_readonly_capable`'s docs for what is deliberately left out: no `<fieldset disabled>` inheritance, no non-form-control `:read-only`). The `:required`/`:read-only`-family invalidation rides the same mechanism `:checked` already does — each is fed into `ElementState` (`stylo_impl::element_state`) so Stylo's own invalidation maps see the dependency and restyle precisely; `:lang()` instead forces a self+subtree+later-siblings restyle on a `lang` write (`PSEUDO_CLASS_ATTRIBUTES`), because its answer is inherited through the nearest ancestor rather than a fact of the element's own state. Still silently dropped: `:has()` — `stylo`'s servo-feature `SelectorParser` answers `parse_has() -> false`, so the selector never even parses into a relative selector; this is an upstream `stylo` crate limitation (fixing it needs a patched/forked `stylo`, the shape of the vendored `wgpu` fork), not a `rinch-dom` bug, and #680 stays open for it. `:focus-within` was attempted for #681 and **reverted**: an eager ancestor-propagated bit went stale under `style_invalidation_twin_tests.rs`'s random-mutation oracle whenever a subtree was `Move`d while focus lived elsewhere (nothing re-derives it on a structural change, only on a focus change) — see `stylo_impl.rs`'s comment at the pseudo-class match's catch-all for the fix sketch. `<img width=100 height=50>` works as of **#684** (the `width`/`height` hints of `<img>`, `<video>` and `<iframe>`; the other legacy attributes are in `legacy_hints.rs`, #1419). The rest of the state family — `:indeterminate` / `:valid` / `:invalid` / `:in-range` / `:out-of-range` / `:default` / `:target` / `:fullscreen` / `:modal` / `:popover-open` / `:autofill` / `:user-valid` / `:user-invalid` — still fall through the catch-all `_ => false` in `match_non_ts_pseudo_class` (no constraint validation, no document/fragment concept, no distinct "default" tracking). `docs/src/guide/theming.md` has the measured table. Everything above works on `rinch-web` (the browser matches), so a rule that works in the browser and not on desktop is probably one of the still-open ones; a class selector is the spelling with no gap on either backend
- **A sizing keyword on `min-width`/`max-width`/`min-height`/`max-height` did nothing**: the intrinsic keywords (`max-content`, `min-content`, `fit-content`, `stretch`, `-webkit-fill-available`) lay out on **`width`, `height` and `flex-basis`** since #691 and are laid out as `auto` on **`min-*`/`max-*`** (#1275). All parse — their stylo preferences (`layout.css.stretch-size-keyword.enabled` and siblings in `stylo_static_prefs`) default to `true`, and `RinchDocument::new` (`set_stylo_prefs`) leaves them alone — and survive as `DimensionValue::Intrinsic`, so `get_computed_styles` reports what the author wrote. `DimensionValue::to_taffy` hands Taffy 0.14 its own keyword, which it lays out on any box it computes as a **child**; `to_taffy_lpa` (Taffy's `min_size`/`max_size`, `LengthPercentageAuto`) has no keyword to hand over, and `from_stylo` prints one stderr line per such property and keyword per process. Two kinds of box Taffy cannot see a keyword on, so rinch resolves it: an **atomic inline** (`inline-block`/`-flex`/`-grid`) is computed as a Taffy *root*, which ignores its own size keyword — `ifc.rs::resolve_root_width_keyword` measures the width at `MaxContent`/`MinContent` and pins it, and `fit-content`/`stretch` (which need the containing block's width) ride `resolve_percentage_inline_blocks`, laying out as `auto` on the pass before the root compute; and a **fixed or ICB-absolute** box bakes `stretch` from the viewport less its insets (`out_of_flow.rs`), and an `auto` size between paired insets the same way, less the margins, before the compute — the read-back keeps Taffy's size (so `min-`/`max-` sizes hold) and only places the box (`out_of_flow::place_fixed`, #2002; it used to stretch an `auto`/`stretch` width to the whole room after the compute). `fit-content(<length-percentage>)` stays `auto`, which is right: Chrome 153 does not accept it on `width`. (`fit-content` around content that wraps is as wide as the available width since #2330, #1276; it was the widest line.) `height: stretch` on an atomic inline is resolved against a definite containing-block height by `ifc.rs::pin_containing_block_sizes`, with its percentage and `calc()` heights and percentage padding (#1277, #1420, #1480; see `docs/internals/positioning.md`). Still not Chrome's, pinned in the `KNOWN` list of `crates/rinch-dom/tests/intrinsic_sizing_twin_tests.rs` (the Chrome 153 twin over block/flex/grid/inline-block/abs/fixed): `width: stretch` on an overflowing flex item (#1277); an **`auto`** atomic inline is shrink-to-fit since #658 (`fit-content` with a containing block, so it wraps there; laid out as `auto` before the root compute, and one that fits stays measured as `auto`), and since #1476 also where the containing block is sized *from* the box — a flex item, a grid item in an `auto` track, a `fit-content`/`min-content` block, a shrink-to-fit absolute box, another auto atomic inline (`crates/rinch-dom/tests/atomic_inline_content_sized_cb_1476_tests.rs`, 39 Chrome 153 shapes). An IFC **measure** lines an atomic inline up at what it contributes to the width asked about, not at `Node::layout` (`ifc::AtomicContributions`; the paint layout still uses `Node::layout`): `Node::natural_inline_size` (the size it had when `resolve_percentage_inline_blocks` first resolved it; read only for a box with a `keyword_inline_cb_width` entry, or a `percent_inline_cb_width` one — any other box has its natural size, and one that became an atomic inline by a restyle has never been measured as one) for max-content and for a width it fits, `NodeTree::atomic_min_content` (a width; the height of a box at a width it has not been laid out at is not known, and the height it has stands in until the pass lays it out there — never the height of its min-content compute, which breaks its text at every word) for min-content, and `max(min-content, width less its margins)` for a width it does not fit — unless the box was resolved against exactly that width, when the size it has is the answer. Only for a box whose width is plain shrink-to-fit (`ifc::plain_shrink_to_fit_margins`: `auto` width, no percentage `min-`/`max-width`, length margins); a percentage or `fit-content` width, or a percentage `min-`/`max-width`, is still lined up at the size it has, so such a box in a content-sized container can still take its full width — except in a **max-content** measure, where a box with a `percent_inline_cb_width` entry is lined up at its `natural_inline_size`: its percentage is cyclic there and counts as `auto` (regress-017: lined up at their resolved widths, a table's `width: 100%` pictures shared the free width by the order they loaded in, since a picture that arrived after the first layout was measured at its natural width and the earlier ones at the narrow columns they had been resolved to; `tests/regress_017_table_columns_tests.rs`). The min-content size is **lazy**: a measure that needs one it does not have lines the box up at its max-content size and pushes the box on `NodeTree::atomic_min_requests` (a measure runs inside a Taffy compute and cannot start one); `resolve_percentage_inline_blocks` first drops the answers measured with such a stand-in (the Taffy and IFC measure caches of each asked box's IFC — a box resolved in that pass is sized by computes that would otherwise be served them), then measures the asked boxes after its own work (`measure_atomic_min_contents`: the min-content compute, then the box as `auto` again, and every atomic inline around it when the answer differs from the max-content width), returns `true`, and `resolve_layout` runs the pass **again after the compute that follows a pass that found a request** (`NodeTree::atomic_contributions_changed`); a pass that found none is followed by one compute and no further pass, as before. `ifc::MAX_INLINE_ROUNDS` (64) is a guard against a cycle, not a budget: a layout that stopped at it would not be a fixpoint, and the next one would carry on (no fixture needs more than four rounds; the guard was 4, and four boxes nested through flex items stopped at it until the boxes inside a box were measured first). A second layout with nothing changed moves nothing (`a_second_layout_with_nothing_changed_moves_nothing`, and after every step of the histories) — except around a **percentage** box in a content-sized container (a `max-width: 80%` box, or a plain `width: 50%` one in a flex item or `auto` grid track): that cycle drifts over several layouts on main too, and an `auto` box in a neighbouring item or track now moves with it (up to seven layouts to settle, review 2 of #1488). The measure of a box (`measure_atomic_min_contents`, and the min-content compute of `resolve_root_width_keyword`) first measures every asked box **inside** it: Taffy keeps a flex item's min-content answer from any compute of the box, made with a stand-in, and would serve it. A capped box is lined up at its **margin box** (`width + margins`), so a container sized from the line leaves it that width once its margins come out; a box that fits is lined up without its margins, as the paint layout lines every box up (pre-existing: a line does not hold an atomic inline's margins). `remeasure_dirty_atomic_inlines` now measures as `auto` the percentage- or keyword-sized boxes **inside** a box before re-measuring it (`reset_resolved_atomic_inlines_inside(.., false)`): a text edit in an `auto` box holding a `width: 50%` box used to size it from that box's last resolved width, and differ from a fresh layout. So a box on a line narrower than itself — which includes every box in a row flex item or an `auto` grid track, whose auto minimum size is a min-content measure — costs two extra computes, once, and that layout one or two extra root computes; a box in a block that fits costs nothing new (`the_min_content_size_is_measured_once_and_only_when_a_line_asks`: 20 chips in blocks 20 computes, in flex items 60, a relayout 0). The entry is dropped when something inside the box changes that can move a size (`mark_atomic_inline_dirty`, which also notes the box in `NodeTree::atomic_min_dropped` so that the line around it is measured again even when the box comes out the size it was — a text edit can change only its min-content width; a colour-only restyle goes through `mark_atomic_inline_dirty_for(.., false)` and keeps it, so a hover costs what it does on main), by a whole-document pass, and when the node is freed (`remove_subtree`); **a new route that changes a box's content without one of those leaves a stale min-content width**. A text edit in a chip in a flex item therefore costs 3 box computes and 2 root computes where main has 1 and 1 (`perf_regression_scenarios::a_text_edit_in_a_chip_in_a_flex_item`; the first layout of ten such rows 60 and 2 against 20 and 1), and a box whose min-content width is its max-content width and that holds a percentage is resolved by one more pass. A capped box whose container is resized is resolved in **one** compute (its max-content width is remembered while it stays resolved, `Node::natural_max_width`), which is still a cost per capped chip per pixel that main does not pay: ten rows of two capped chips, 20 box computes and 2 root computes for a 1px resize (`a_one_pixel_resize_with_every_chip_capped`). Not Chrome's: the 1px "fits" tolerance (a 380.9px box in a 380px block is not wrapped). Since #658 `resolve_percentage_inline_blocks` resolves outermost first, measures the boxes it resolves inside a box as `auto` again before resolving it (or the scoped and whole-document passes disagreed, #1327), and lays the atomic inlines around a box it resized out again at their own width (they used to keep their old height; re-sizing them instead shrank an `inline-block` around a `width: 50%` child, #662). **`grid-template-columns: max-content` works** too (Taffy track sizing).
- **An empty `<div>` is 0 tall** (#296): a block with no in-flow content has
  no line box, so its auto height is its padding and border — CSS 2.1 §10.6.3,
  Chrome 153, and `rinch-web`. rinch used to floor every childless block at one
  line, a divergence written for `<input>`/`<textarea>`, which had no content
  height, and which was quietly also giving a blockified `<br>` and every
  non-text `<input>` type their line. It over-applied (it ate padding, reached
  `display: grid`, inflated block images and overrode `min-height: 0`) and is
  gone. An empty block that should hold a line says so: `min-height: 1lh`, as
  the editor's empty paragraphs do. **Line-sized controls are measured** (#297,
  `crates/rinch-dom/src/form_control.rs`), through a Taffy measure
  (`NodeContext::FormControl`) with the padding and border on top: a
  `<textarea>` is `rows` lines (default 2; `rows` is read by HTML's rules for
  parsing non-negative integers, #1153 — `"3abc"` is 3, `"1e1"` is 1, `"inf"`
  is 2), a `<br>`
  one line, and an `<input>` one line for every `type` but `checkbox`,
  `radio`, `range`, `color`, `image` and `hidden` — an invalid `type` is a text
  field, as in HTML. It is a measure, not a `min-height`, so `min-height: 0`
  lets the control shrink in a flex column and `max-height` caps it, as in
  Chrome. A control whose children form an inline formatting context is left
  *hollow* by the IFC pass (#1159): its Taffy node carries the same
  `FormControl` measure a childless one does, no inline layout is built for it,
  and a `<textarea>`'s direct text children are its default value
  (`form_control::control_value`: the `value` attribute if present, even `""`,
  else those children), which `paint_input_value` draws and the desktop shell
  edits from. The attribute's presence is the textarea's **dirty value flag**
  (#1186): the shell writes it at the first edit (even one that leaves the text
  unchanged — anything the command pushed on the undo stack) and at a
  composition's first preedit (Chrome's `.value` holds it), never at a focus,
  a blur or a caret move (`sync_input_cursor_to_dom` skips `value` for a
  pristine textarea still showing its children), so a child change shows until
  then — while focused too, with the caret kept at its UTF-16 offset, clamped
  (`replace_keeping_offsets`, Chrome 153). `rinch-web` follows the same rule by
  leaving it to the browser (#1206): `set_text_content` sets the text and no
  longer writes `.value` from it, which #100 had done on every change, dirty or
  not. So a text child is a *default*, not a controlled value, on both backends:
  a controlled textarea is `value_fn` / a reactive `value:`. `value` writes agree too
  (#1222): a write equal to the shown text sets the flag on both (the web's
  `sync_reflected_property` performs the equal `set_value` for a textarea,
  which moves no cursor), and `remove_attribute("value")` is a write of `""`
  that leaves it set — on the web `.value = ""`, on desktop
  `Node::value_dirty`, the one dirty state the attribute cannot carry, so
  `control_value` answers `""` with no attribute. Nothing clears it again; a
  browser's form reset does, and desktop models none. An `<input>`'s children are not drawn, and an element child of either
  control has no box at all (UA `display: none !important`, #1178). **Its width comes from `size`
  / `cols`** (#1177), as in Chrome 153 at a device scale factor of 1 (Chrome
  computes in device px, so at 1.5 it can differ by several px): the primary
  font — the face the stack resolves a Latin `x` to, never a lone digit, which
  fontique can send to a colour-emoji face — and its OS/2
  `xAvgCharWidth` scaled to the font size (`avg`, used as `max(avg,
  round(avg))`, read off Chrome's output) times `size` for a text-like
  `<input>` (default 20; `number` is always 20) plus the font's `head` extent
  `round(xMax - xMin)` less one `avg`, or times `cols` for a `<textarea>`
  (default 20) plus a 15px scrollbar gutter unless `overflow-y` is
  `hidden`/`clip`; both read by HTML's non-negative integer rules, 0 or invalid
  meaning 20, and cached per node against the font and the document's
  `font_generation` (`shape_form_control_metrics`; `RinchApp::register_app_font`
  calls `RinchDocument::note_fonts_registered` for a live document, which
  re-sizes every control). An average above 1.7 × the face's `0` advance — a
  CJK face's full-width one — is not trusted: Chrome then uses `ceil(zero ×
  size)` (textarea `+ 15`), unrounded and with no extent term (measured by
  rewriting only the OS/2 value, on Noto Sans CJK and Inter).
  It is the measure's answer at every available width, so an author `width` or
  `max-width` wins and a narrow container overflows rather than shrinks it. Not
  modelled: the other `<input>` types' widths (the date/time family, the
  buttons, `file` — 0 wide, as before), a `display: block` control's
  shrink-to-fit (Chrome keeps the intrinsic width; rinch fills), Chrome's
  per-family exceptions (`system-ui`'s fixed extent), the six excluded types'
  own sizes (13x13 checkbox, 16px range, …), the date/time family's extra 2px, and a `line-height` below the
  font's normal line (Chrome clamps up). Line boxes rinch still gets wrong
  around empty content: #1154
