# Rich-text editor (model, view, collaboration)

Read this page when your task touches: anything under rinch-editor-*, the Editor component, EditorHandle, collaboration.

Moved verbatim from `CLAUDE.md` on 2026-10-22 (the index there points here). New mechanism notes for this area go on this page, not in `CLAUDE.md`. A code comment that cites a `CLAUDE.md` section by name means a section now on one of these pages: `grep -rn '<name>' docs/internals/`.

## Rich-Text Editor

Rinch's rich-text editor is a ProseMirror-style, **model-first** editor. The document lives in `rinch-editor-core` (a pure, wasm-clean crate: `Node`/`Mark`/`Fragment`/`Slice`, one char-based `Pos` space, a real `ContentMatch` schema, invertible `Step`s, `Transaction`/`EditorState`, plugins/commands/keymap/input-rules, a single Step-based history). The view lives in `rinch-editor-view` — **renderer-agnostic**: it projects that model onto any `rinch-core` `DomDocument` host and renders the caret/selection from `Selection` after layout, so desktop (rinch-dom) and web (`web_sys`) share one view. On desktop it arrives with the `desktop` feature and `crates/rinch/src/editor/` re-exports it; on web, `rinch-web` re-exports it. There is no `contenteditable` attribute engine anymore — mount the `Editor {}` component instead.

**Mutation flows one way:** every edit is a `Transaction` applied by `EditorState::apply` → the view diffs old/new doc + decorations and patches the DOM. Commands read **state**, never the DOM. A command that edits many places at once states them as `BatchEdit`s in the starting document's coordinates and applies them as **one** `BatchStep` (`Transaction::batch`, #1200): it builds the document the equivalent `ReplaceStep`s/`SetNodeAttrStep`s build one at a time (two changes of one attribute: the last wins) and its step map maps positions as theirs did, but it keeps one document, not one per edit; it checks content on the result only, a rebase (`Step::map`) maps each construction-merged range as one replace (deletions that met delete a concurrent insert between them) and folds two closed replaces it brings end to end into one (with an open slice the later edit's content is lost), and a selection the command leaves is mapped once (about 0.6% of table commands leave the selection where the per-row commands did not). See `docs/src/guide/editor.md`. Every table command does; as a step per row, `addColumnBefore` on 16,000 rows was 6.4 s and 2.1 GB, now 29 ms.

**Undo groups typing by time** (#940): the history merges consecutive typing transactions (any transaction made only of non-structural replace steps: text inserts and deletes, Backspace and the word deletes, and also an inline picture or a plain-text paste, which join a run they land in) less than 500 ms apart; a structural edit (split, mark, block change) is a step of its own, and a caret move, a stored-mark toggle, an undo and a redo each end the group (the last two since the review of #1612: typing right after one used to join the group on top of `done`). The core reads no clock; `EditorHandle` stamps every local edit it dispatches — `update` and the input paths (`dispatch_inner`), `command`, and the commands `insert_image`, `insert_image_at` and `toggle_link` run (`run_stamped`) — with `rinch-editor-view/src/clock.rs`'s millisecond clock (`web_time`, since `std::time::Instant::now` panics in a browser) unless its builder called `Transaction::set_time` itself, which must read the same clock (`history_now_ms()`): a time on another clock (epoch ms) stops the next keystroke merging. Before #940 nothing stamped a time and every run of typing was one undo step until a caret move. Tests place keystrokes on either side of the window with the doc-hidden `__set_history_clock`. Pins: `rinch-editor-view/tests/history_time_940.rs`, `rinch-web/tests/editor_history_time_940.rs`.

**The history maps through changes it did not record** (#1249, #1615, #1856; reworked after the review of #1889). `plugins/history.rs` is a port of prosemirror-history's `Branch` on a **persistent list** (newest item first, `Items`): each item is a step's forward `StepMap`, its inverse, and on an event's first item the selection and typing flag; map-only items are a change the history did not record (`peer`) or the map of a step an undo applied. Cloning the state per transaction is a pointer copy; recording is O(1). A doc-changing transaction with `add_to_history(false)` (a collab peer's integration, `ORIGIN_REMOTE`; the oversized-table cure) adds its maps to both branches (`add_maps`), **folded into the previous item when that is a peer map too and the fold is exact** (second review of #1889: folding every touching pair lost the position between a peer's deletion and their insertion, so an undo deleted their char or dropped my restore). `StepMap::compose_exact` merges ranges that overlap or touch only after checking every position of the merged range against the two maps in turn (position, `deleted`, `deleted_after`, `deleted_across` — the flags a step reads); a run of typing folds, an insertion beside a deletion does not. A run of one-char deletions (a peer's Backspace or Delete) is kept as a count, `unit_run: (at, n)`, and expanded into its `n` maps only when an undo maps through it, which is exact. So a peer typing or backspacing for an hour is one item between two of mine; other peer changes that do not fold cost one small item each until the events before them are dropped. Events past the depth cap are hidden at once and dropped from the list 20 at a time (PM's `DEPTH_OVERFLOW`), with the maps before them. `pop_event` walks only the newest event and what follows it; once it meets a map-only item it maps each step through a slice of one `Mapping` (`Mapping` shares its maps behind an `Rc`, so `slice` copies none), mirroring each applied step's map to the original's (`mirror_offset`) — only when the two have as many ranges, since recovering a deleted position takes the mirror's range of the same index: a mapped `BatchStep` drops each replace a later change deleted across and may still apply (a `mergeCells` undone after a peer's integrate replaced the table), and mirroring its shorter map panicked in `StepMap::recover` (#1935, `tests/history_merge_cells_1935.rs`) — and maps the selection the same way. **An undo or redo repairs the tables it left ragged** (#1937, #1847's decision: repair, don't skip): a mapped table command can apply in part (a `mergeCells` undone after a peer's merge restored cells into the peer's table and kept the spans), and a ragged table is `Unsupported` to collaboration, so the undo reached no peer and every edit after it stalled outbound. `hist_transaction` calls `Transaction::repair_tables_after_history`, in the undo's own transaction, with the selection mapped through the repair. It runs only when a change the history did not record came after the event: `pop_event` met a map-only item, or an item marked `unmapped_after` (a peer's change that moved no position, a cell's `colspan` among them, gets no map from `unrecorded_maps`, so `add_maps` would leave no trace of it; `Branch::note_unmapped` marks the newest item instead — the review of #1950's differential found the undo of a deleted row beside a peer's widened cell left ragged without it). A local undo applies the recorded inverses to the very documents they were made for and brings back the document before the event, table for table, so it checks nothing. Per step it looks only where the step can have changed a grid: an inline insertion (a closed slice of inline nodes at one position, which only a textblock takes) is not looked up; a range inside one textblock that puts in no table, row or cell is found so by `inside_one_textblock`, one walk down the document the step applied to (the undo of typing, while it still is: the first round skipped every undo of typing on a flag recorded with it, and a peer who moved half of my pasted text into a new cell made that undo a delete across two cells — review of #1950, `s21`); another step inside one cell that puts in no table part resolves its start once and is done; a step across cells, a `BatchStep` (its replaces and its attribute positions), a `colspan`/`rowspan` set on a cell, and a slice that puts table parts in while open at either end (the inverse of a delete from one row's cell into the next row's: put in at one point inside a cell, it splits the row around it — the first round looked only inside its range) look at the tables around them; a closed slice that puts table parts in inside a cell looks inside its range. A table found ragged that was ragged before the undo (through the inverted mapping) is left as it is; the rest go through #1931's `repair_table`, innermost first. Measured (`editor::undo_in_table`): undoing a keystroke in a 1000-row table 78,959 → 79,057 instructions (local: nothing looked up), and after a peer's keystroke 84,069 → 94,160: the walk down to the step's textblock scans the table's rows, as any position lookup does (`Fragment::find_index`), and a sound skip needs it. Pins: `history_merge_cells_1935.rs` (the #1935 history), `history_table_repair_1937.rs` (a randomized history that must leave tables tiling after every undo and redo; the review's scenarios as named tests; and the **differential**: one random history from the review of #1950 — table commands, typing, pasting, Enter, hard breaks, deletes within and across textblocks, text moved — run with the repair looking where it looks and with it looking at every table after every undo, local ones too, which must give the same document at every step, and a second mode beside a table that was ragged from the start, where the full scan runs where the repair runs and the old table must stay as it is; `__set_full_repair_scan`, a `#[doc(hidden)]` test seam; `RINCH_UNDO_TILE_SEEDS`, 5000 clean), `undo_among_peers_1249::s20`/`s21` (two sessions: the undo records and outbound keeps sending), and the collab fuzz's `fuzz_undo_among_grid_changes_keeps_tables_tiling` (all three delivery modes; its counters are per test thread). A step that does not map or apply is skipped (PM's `maybeStep`); an event whose steps all fail is still popped. **An inverse delete of typing a peer has since typed inside** is split around their text (`split_delete`; PM maps it as one growing range and deletes theirs too). The popped branch travels to `apply` in the transaction's meta (`HistoryMeta`). **The maps of an unrecorded change are reconstructed** (`unrecorded_maps`): the collab integration replaces every block a peer changed, so the history diffs the range before and after, as tokens of one position each (a char whatever its marks, a block's open and close whatever its type, a leaf by type), trims the common ends and runs Myers on the middle (`token_diff`, up to 64 edits, else one range). A transaction of several replaces is diffed as one range, so a block moved by a delete in one step and an insert in another is found as a move. A peer's bold, heading or alignment therefore moves no position. Identical content is ambiguous to a diff (#1895: the fix is mapping through yrs's own insert/delete events). Work counters `plugins::__history_work` and `transform::step_map::__step_map_clones` hold the cost flat. PM fidelity fixes the undo exposed: a mark step's re-marked copy joins the text nodes it leaves equal (`Fragment::from_array`), and `Slice::insert_at` checks that the node content goes into takes it (`canReplace`). Pins: `rinch-editor-core/tests/history_remote_1249.rs` (cost pins at the end), `rinch-editor-core/tests/history_props_1249.rs` (a snapshot model of local history; peers' updates; command and paste output hashed against main), `rinch-editor-collab/tests/undo_among_peers_1249.rs` (two real sessions, s01–s19 and a random trial; #1895's cases are `known_wrong` pins), the `1856_seed_*` and `same_line` tests in `typed_once_1850.rs`, `fuzz_undo_and_redo_among_remote_changes` in `fuzz.rs`, and the `rv6_undo_*` tests.

**Persisting content:** `DocNode` (serde) is the durable wire shape — `Node::to_doc()` / `Schema::node_from_doc()`, plus total HTML/markdown serializers in `rinch-editor-core::serialize`. Enable `serde` on the `rinch` facade (→ `rinch-editor-core/serde`). **Task lists go through Markdown and HTML** (#1365): `doc_to_markdown` / `doc_from_markdown{,_strict}` write and read `task_list` as GFM `- [ ]` / `- [x]` (a marker in an ordered or mixed list is refused by strict and kept as text by lenient; a bare `- [ ]` is an empty item), and HTML copy-out is TipTap's `<ul data-type="taskList">` > `<li data-type="taskItem" data-checked>`, which `slice_from_html` reads; a pasted task list is fitted like any list (below), and in a collaborating editor stalls outbound (A22). Guide: `docs/src/guide/editor.md`. **A load caps `colspan` at 1000 and `rowspan` at 65534** (Chrome's limits, #1214, #1244): `tables::cap_spans` (`cap_colspans` is its deprecated old name), called by `node_from_doc`, `EditorHandle::new` and `load_doc`, as the HTML import reads them; one `colspan = 3,000,000` cell made a 2^21-column grid and `addRowAfter` 2 M cells (15.6 s, 5 GB). Edits are not capped. **Nothing caps a row's width, on load or paste** (#1244 removed the paste-only `MAX_IMPORTED_ROW_WIDTH` cut and its rowspan-1 rewrite, so `slice_from_html` and `cap_spans` give the same spans; the paste still cuts a rowspan at its row group's end and pads short rows within `PAD_CELLS_PER_CELL`): a row of 2,100 `colspan = 1000` cells is 2.1 M columns, mapped at the slot budget. **`addRowBefore`/`addRowAfter` copy the spans of the row beside the line** (`table_ops::add_row(info, row, like, …)`, `like` = `row - 1` after, `row` before): a cell crossing the line grows its rowspan as in ProseMirror; each free run gets `make_empty_cell_spanning` cells at `like`'s boundaries, cut at the run's edges; holes in `like` get a cell per column while the holes number no more than `max(table's cells, HOLE_CELLS_FLOOR = 1000)`, else cells of `MAX_COLSPAN` (without the floor a `colspan = 10` title over rows of 2 cells gave `[1, 1, colspan 8]`, review of #1876); cells are always plain `table_cell`. On a table with no merged cells the row is byte-identical to the old one-cell-per-column row (pinned by `tests/add_row_copies_spans_1244.rs`, whose `the_issues_loaded_table…` pins 2,098 cells where 2,097,152 were built). `table_commands_one_step.rs`'s `reference::add_row` states the same rule column by column. **`deleteRow`/`deleteColumn`'s one-line-at-a-time fallback** (overlapping cells, or cells in no slot past the slot budget) runs only while `(lines − 1) × map slots ≤ FALLBACK_SLOT_BUDGET` (2^22, `table_ops::one_at_a_time_fits`); past it they use the one-pass `remove_rows`/`remove_columns` (#1874: a recompute per column of a 2^22-slot map made a whole-row delete take hours). Those one-pass walks look a cell up in what they found before calling `cell_rect`, which walks back to the cell's origin (a row of 1000-wide cells was 1000 steps a column), and `TableMap::cells_in_rect` dedups with a set. Pinned by step counts in `tests/table_delete_bounded_1874.rs`. **An image keeps an app's `data-*` attributes** (`NodeSpec::data_attrs`, leaf node types only — `SchemaBuilder::build` panics otherwise — which the starter kit's `image` sets; `schema/data_attrs.rs`): any valid HTML custom data attribute name rinch does not reserve, as a string, through validation (`compute_attrs`), `DocNode`, HTML (written as itself on the void element, read back from `<img>`/`<hr>`/`<br>`), Markdown's HTML tables, collaboration (one `atoms` entry per attribute) and the view (stamped on the host element, removed in place). `is_app_data_attr` is the one test, and `RESERVED_DATA_ATTRS` / `RESERVED_DATA_ATTR_PREFIXES` (`data-pm-*`, `data-rinch-*`, `data-text-sel*`, `data-cursor-*`, `data-selection-*`, `data-tcm-*`, `data-rid`, each exact `data-on…` event name, `data-block-index`, `data-type`, …) the one exclusion list: a reserved name is never kept, read from HTML or stamped. **A new runtime `"data-…"` literal must be reserved or listed safe** in `rinch-editor-core/tests/data_attr_ratchet.rs`, which scans every crate's non-test Rust sources for `"data-…"` literals, `[data-…` selectors and built names (`format!("data-{…}")`, a bare `"data-"` outside the name rule) (a pasted `data-tcm-item` made a press on a picture run a text-menu item, review of #1518). Bounded by `kept_data_attrs`: at most `MAX_DATA_ATTRS` (32) per node, values at most `MAX_DATA_ATTR_VALUE` (1024 bytes), names at most 64 bytes, the first of a repeated name; past a bound the attribute is dropped whole. The bound is the model's (`data_attrs::bound_node_data_attrs`, in `Node::new_branch` and `Node::with_attrs`), so `create_node`, a raw `SetNodeAttrStep` and a node collaboration builds from an unbounded peer's update all hold what HTML, `DocNode` and the view keep (`image_attrs::a_peers_data_attrs_past_the_bounds_are_bounded_on_receive`). **The default paste keeps them only from rinch's own copy-out** (`slice_to_html` marks such an element with `data-rinch-clip`, `CLIPBOARD_MARK`; `replace_selection_with_html` reads with `slice_from_pasted_html`), so another application's `data-*` is dropped; `load_html` / `slice_from_html` keep them all, and an app's own markup through `replace_selection_with_html` keeps them when it carries the mark. The mark filters noise; it is not a trust boundary. An attribute a spec neither declares nor keeps is dropped by validation and not written to HTML. Collaboration builds an atom's attrs in one pass (`Attrs::from_iter`; an `Attrs::with` per attr was quadratic: 4000 attrs took 1.5 s to record), pinned by `image_attrs::an_images_attributes_cost_linear_copies_in_collaboration` on `model::attrs::attr_entries_copied` (behind the test-only `cost-counters` feature of `rinch-editor-core`, which only collab's dev-dependency turns on).

**Embeds (node views, part A).** The starter kit has `embed`: a selectable block-level leaf atom (group `block`, no attrs of its own) that keeps an app's `data-*` attributes exactly as `image` does (`NodeSpec::data_attrs`: same reserved names, bounds and copy-out-only paste rule). It is the block an app will draw a live component into (node views, parts B and C); today the view renders an empty host `<div data-pm-type="embed" data-…>` that the stylesheet gives `min-height: 1lh` and, while empty, a dashed border. Commands, arrows and node selection treat it exactly as a `horizontal_rule` (`rinch-editor-core/tests/embed_node.rs` runs the two side by side). **Backspace at the start of the block after any selectable leaf atom, and Delete at the end of the block before one, select the atom** (`commands::select_atom_across`; the cut is found up the tree as for a join), and an empty block right beside it is removed in the same step; the second press removes the atom. This is a decision (Joe, 2026-10-19), and a deliberate difference from ProseMirror: its base keymap runs `joinBackward` first, which **deletes** the atom in one press when the caret's block is not empty (`selectNodeBackward` only runs after it), and `joinForward` deletes the atom after it, from an empty block too. rinch selects first because an embed can hold an app's component and its state; it applies to a horizontal rule and an image too. They used to do nothing there (`tests/backspace_selects_atom.rs` pins it). **HTML**: a block leaf whose spec has no `parse_html_tags` (`serialize::html::writes_as_div` — `embed`, or an app schema's own) is written as `<div data-pm-type="NAME" data-…></div>` (`data-rinch-clip` on the copy-out, always, data attributes or not) and read back from a `<div>` carrying that marker wherever a block can stand — by a load whatever is inside it, by the default paste only beside `data-rinch-clip` (review of #1565: another application's marked `<div>`, e.g. a browser copy of a page showing an app's export, is read as a container, so its text is kept); `data-pm-type` passes the reader's attribute filter for that alone, and a `<div>` without it is a container as before. `serialize::set_html_fallback(|node| -> Option<String>)` (per thread, a stack of registrations released by `HtmlFallbackGuard`; the callback runs with nothing borrowed) puts an app's markup **inside** that element in `node_to_html` and `slice_to_html`; the reader ignores the element's children, so exported HTML and a copy read back as the same embed; the markup must be valid inside a `<div>` (no bare `<li>`/`<td>`/`<tr>`: in an embed inside a list item or a table cell they close the outer one on read). A guard owned by a fallback is released with it (the entry is dropped after the registry borrow ends). **Markdown** writes the bare element (`node_to_html_bare`, also used for HTML tables) as an HTML block, a newline in a value as `&#10;`; both readers take it back, strict only when the block is exactly what the writer writes (`html_div_atoms`), and a table written as HTML may hold one (`dropped_table_attr` takes the schema now). **Collaboration** needed no change: `embed` is a leaf block atom by the projection's predicate, and a block's `attrs` map already merges per key (`rinch-editor-collab/tests/embed.rs`: different keys both kept, same key converges, removal kept, bounds hold on receive). A remote change of an embed's attrs arrives as `SetNodeAttrStep`s since part B (below).

**Node views (part B).** An app draws its own live component in place of a leaf node: `EditorHandle::register_node_view(NodeViewSpec::new("embed", |scope, ctx| …).matches(|attrs| …).on_key(…).on_caret_enter(…)) -> NodeViewRegistration` (`rinch-editor-view/src/node_views.rs`; dropping the registration releases it, so a component calls `.keep()` to tie it to its own scope, `#[must_use]`; first registered spec that matches wins; only a **leaf** node type can have one). The view's `RenderScope` is owned by the node's `ViewDesc` (`ViewDesc::slot`, an `Rc<Slot>`): mounted when the host is built, disposed (scope first, then its root) when the node leaves; the editor never diffs, measures or decorates inside the host, which carries `data-pm-node-view` (`NODE_VIEW_ATTR`) while mounted. **`matches`, `render`, `on_key` and `on_caret_enter` never run under the core borrow**: the diff only queues `node_views::Work` on the view, which `CoreMutGuard`'s drop takes and runs (`node_views::run`) after releasing the borrow — every path that patches the DOM goes through a mutable borrow, so a new one needs nothing; `render` runs untracked with the view's scope as owner, the others inside their registration's owner (a dead owner is not called). `NodeViewCtx { attrs, selected, read_only, dark_mode }` are `Memo`s over signals the mount owns, written only when the value changed; its verbs: `pos()`, `set_attrs(|&mut Attrs|)` (one `SetNodeAttrStep` per changed key — undoable, sent per key, refused read-only), `delete()`, `select()`, `return_focus()`, `editor()`. `EditorHandle::insert_embed(attrs)` is `insert_block` of an embed. **Decision (d): a view is never handed another node.** `ViewDesc::update` keeps a slotted desc only for the same `Rc` or for a **kept** node of the transaction: one its `SetNodeAttrStep`s changed, with where it stands now and the node it was when the transaction started (`handle::kept_nodes` → `node_views::Kept`; a node an earlier step put in place — a replace, then an attr set on what replaced it — or a later step removed is not one, review of #1575 F4), from `dispatch_inner`, `command` (which runs the command's own dispatch so undo/redo keep it) and the collab integrate. The proof is an **argument** of `EditorCore::commit`, never a field: a refused edit left it behind for the next commit, and a `load_html` handed the old view the loaded embed (F2). Anything else at that place (an identical twin, a replace, a move, an undo of a delete) is rebuilt and remounted. A changed stretch holding a view is diffed by node identity (`ViewDesc::diff_stretch_keyed`): a view's node that only moved within it keeps its mount, and so does a kept node moved by a block inserted before it in the same transaction; a subtree holding views is detached and its discard deferred until their scopes are disposed (`retire`). A `render` that sets its own node's attributes mounts once: a sync during the render (`SlotState::mounting`) is deferred and run once the mount is stored (F7) — a refresh when the same spec still matches, an unmount or a remount when the render's own write changed which spec matches, bounded at 8 nested re-matches so two specs that flip each other settle (N5 of review 2): at the cap the last view stays mounted with refreshed memos although its spec no longer matches the node, until the node next changes (`review3_1575::n5_at_the_cap`). **Collaboration**: `CollabSession::integrate_incremental_transaction` returns the transaction, built from the CRDT block of every leaf **block** atom before and after the update (`remote::AtomIds`, noted in model-build order by `CollabDoc::to_doc_with_atom_ids`, so a table no longer hides them): an atom that is **another block** is replaced even when equal by value (two equal embeds a peer swapped, F1 — a diff by value saw no change and left the receiver's views on deleted blocks), one that is the **same block** with other attributes gets `SetNodeAttrStep`s, and every other changed block is replaced on its own (`remote::changed_middle`), so an attr change beside a peer's typing in one update (a reconnect) keeps the mount (F3). The "before" ids come from the previous operation (`atom_cache`: per session, keyed by the model document's `Rc` and a CRDT generation bumped by every session call that can change the CRDT — `record_local*`, an integrate, `merge`, `delete_oversized_table`; filled by `new`, `projected_doc`, every integrate and a `record_local` whose changed middle holds no atom, and not by a `record_local` in a document holding no atom, which then walks no block for it: `projection_cost::a_local_keystroke_after_a_remote_change_walks_no_block_without_an_embed`, N3 of review 2), so at steady state a remote keystroke reads the CRDT once with or without an embed (`projection_cost::a_remote_keystroke_beside_an_embed_reads_the_crdt_once`; it was a second whole read, +50%, F5); on a miss — a local edit that wrote an atom, a guest's first operation, a session used from another thread — it reads before the update too, only while the model holds an atom. **While outbound is stalled (#220)** the model is not the CRDT's read, so nothing is read for it: a local edit the CRDT refused carries the blocks of the atoms it provably kept (`CollabSession::carry_unprojected` / `carry_ids`: the blocks shared at either end, an atom moved as the same `Rc`, an attribute change the editor proved) and marks every other atom **unproven** (`atom_cache::unproven`, equal to no block), so a peer's change during the stall keeps those views mounted (an attribute change included) and remounts the rest, never re-pointing one; and the re-base that ends the stall, which pairs blocks by value, is checked against those blocks (`settle_rebased_atoms`): an atom that landed on a block it was not proven to be — two equal embeds reordered during the stall, a copy pasted before its original — is written again as a new block, so the peers' views of the old block remount instead of being edited by another node's view (N1/N2 of review 2; pins `review2_1575::s1*`, `s2`, `s9`–`s11`). A peer's change during a stall still brings every block that differs from the shared document back to it (#220), dropping the unsent edits there, a view's own attribute change included (reverted, not remounted). A view-less descriptor is never patched into a node a registered spec draws (`ViewDesc::update`): a task list's host is a `div`, as an embed's is, and an embed put in its place got no view. Nor is any element descriptor patched into a node of another type, whatever the tag: a host of one `div` type kept its `data-pm-type` in another's place (F2 of review 3). A remote integrate whose CRDT read differs from the model (a previous integrate failed after yrs applied part of an out-of-order update) treats every atom as unproven, so equal embeds are remounted rather than paired by value (F1 of review 3, `review3_1575::t1_*`). **One `Rc` in two places** (an in-editor copy pasted beside its original) is one node to `same_ref` and two CRDT blocks: for a **peer's** change the descriptor diff follows that transaction's mapping for such a node (`Cx::same_place`, `RinchDomEditorView::set_remote_mapping`), so a remote step that replaced one copy does not hand that copy's view the other copy's place (it took the first `same_ref` match, and a stalled peer's view ended on another embed's block, which the stall's cure then showed: round-3 review of #1595, F3, `review3_1575::f3_seed_5730_*`); a local edit keeps the first match, which is the pairing the projection's identity runs make, and a kept node is matched with the copy at the position its `SetNodeAttrStep` names (`Kept::old_pos`). The view-level fuzzes (`review2_1575`, `review3_1575`) build their sessions with seeded yrs client ids (`EditorHandle::start_collaboration_host_with` / `_guest_with`, doc-hidden, fed by `rinch_editor_collab::testing`'s pinned sessions through the view's dev-dependency), so a seed replays; `R_ID_SALT` picks another set of ids for the same seeds. With random ids seed 5730 failed about half its runs and passed 1000-seed runs by luck. ### Mounting an editor (the public API)

```rust
use rinch::prelude::*;

#[component]
fn app() -> NodeHandle {
    let editor = create_editor();           // -> EditorHandle (cheap to clone)
    let ed_bold = editor.clone();           // one clone per closure
    rsx! {
        div {
            button { onclick: move || { ed_bold.command("toggleBold"); }, "Bold" }
            Editor {
                editor: editor.clone(),     // optional; omit to self-create a handle
                content: "<h1>Title</h1><p>Hello <strong>world</strong></p>",
            }
        }
    }
}
```

`anchor_selection() -> SelectionAnchor` captures the selection for an insertion that
completes **later** (an async paste, an image upload, a model completion). Every
document-changing transaction maps the anchor forward through its steps, so
`anchor.selection()` still points at the content the user aimed at however much they
typed meanwhile; it answers `None` once the document is *replaced* (`load_doc`/
`load_html`), and the anchor releases itself on drop. **A remote collaboration change
carries it too** (#1457): `integrate_remote` and `collab_delete_oversized_table` call
`EditorCore::carry_anchors_remote`, which uses `rinch_editor_collab::RemoteCarry` — the
rule the live selection is carried by (`remote.rs`: the block-level step map outside the
top-level blocks the peer changed, `carried_position` inside a textblock the peer typed
in), except that where the live selection is re-anchored to the nearest valid place, an
anchor answers `None`: its block was removed, split, joined or changed kind (the changed
run has a different block count before and after), and "nearby" would be a guess. It used
to die on every remote change. Pins: `rinch-editor-view/tests/review_1433.rs` `collab::c1`
to `c5`. This is
what makes the asynchronous Ctrl+V (#149) land in the right place — desktop's
`dispatch_editor_paste` anchors, reads the clipboard off-thread, then inserts at the
anchor.

**Seeing and rewriting a paste: `Plugin::handle_paste(&self, &EditorState, &PasteContent) -> Option<Transaction>`.** Every paste the platform reports as a paste event goes through `EditorHandle::paste(&PasteContent { text, html })`: desktop's Ctrl+V, Ctrl+Shift+V and context-menu Paste (`apply_paste_at_anchor`, at the anchor, in `event_dispatch.rs`) and the web's `paste` event (`on_paste`, `editor_input.rs`). A mobile keyboard's clipboard chip inserts text directly (`insert_text` / `beforeinput insertText`) and does **not** reach the hook. It asks `EditorState::handle_paste`, which offers the paste to each plugin in order; the first `Some` is dispatched as the paste (one transaction, so one undo step; `input: true`, so it scrolls; `commit`, so read-only refuses it and collaboration records it), and a claim that is refused does **not** fall through. No claim: html (`replace_selection_with_html`), else text; in a `NodeSpec::code` textblock the text flavour whenever there is one, verbatim. An empty paste asks no one; an image-only paste never reaches the hook (desktop's `RichPaste::Image`, the web's image-file branch). Desktop reads the text beside an html answer in the **same** clipboard job (`rinch_clipboard::paste_rich_with_text_async`), so a plugin sees both flavours on both platforms: a copied link's html is an `<a>` whose text may be a title, and the text is how a plugin tells a pasted URL. The web keeps its order html → image file → text: a bitmap with no html goes in as an image, as desktop's probe orders it. `set_paste_interceptor` still skips editor pastes; this is the editor's hook. Pins: `rinch-editor-core/tests/paste_hook.rs`, `rinch-editor-view/tests/paste_hook.rs`, `rinch/tests/editor_paste_hook.rs` (a real Ctrl+V through the clipboard worker; its own process because the completion needs a registered main thread), `rinch-web/tests/editor_paste_hook.rs`.

**A paste is fitted, not just replaced** (#1382): the default paste is `Transaction::replace_selection(slice)` → `Transform::replace_range`, ProseMirror's `replaceRange` + `Fitter` (`rinch-editor-core/src/transform/fit.rs`), where it was a raw `tr.replace` that refused any block at a caret and fell back to `text/plain`. One step (a `ReplaceStep`, or a `ReplaceAroundStep` when the text after the caret moves into the pasted content) or nothing. Content open at the slice's start continues the textblock, the rest keeps its structure, the tail after the caret joins the textblock the slice ends in (`<p>a|bc</p>` + a two-item list = `<p>aA</p><ul><li>Bbc</li></ul>`); a closed block (rule, table) splits the textblock and leaves no empty block at its edge; over a whole textblock (an empty line included) a slice that starts in a **`NodeSpec::defining`** node replaces it (`list_item`, `task_item`, `heading`, `blockquote`, `code_block` — so a pasted list, heading or quote on an empty line is that block); list items pasted in a list are sibling items. `slice_from_html` opens each edge down to the textblock there (a list is open 3/3, a table or rule closed), `clipboard_slice` (what `selection_clipboard` cuts) keeps the list or table around content the top node does not take, so copied items say which list they were in. **Not ProseMirror's:** no node is created (`fillBefore`) or wrapped (`findWrapping`) to make a fit valid — `ContentMatch` is a part list, asked through `matches` / `matches_prefix`, not a DFA — so such a fit fails; a fit never leaves the isolating node the range starts in; a range across two isolating nodes gets the plain `replace` only. Two reader bugs went with it: a void `<meta>` / `<link>` was skipped by looking for its end tag, which dropped **everything** after the `<meta charset>` Chrome and Firefox put first in what they copy (such a paste was plain text), and an inline element around blocks (Google Docs' `<b style="font-weight:normal">`) flattened them into one bold line — it is a container now, and a mark element around blocks (`<a href><h3>…</h3><p>…</p></a>`) puts its mark on the inline content inside them (`with_mark_inside`), except a `<b>`/`<strong>` whose own style says `font-weight: normal|400`, which is no mark anywhere. A list directly inside a list (Docs: `<ul><li>a</li><ul><li>b</li></ul></ul>`) nests under the item before it, and any other non-`<li>` child with content gets an item of its own (`list_item_contents`; they were dropped). All reader changes reach `load_html` too. **The HTML reader is total about text** (#1397, #1392, #1401; `serialize/html_tree.rs` builds the tree, `html.rs` maps it): no markup is refused, the text of every element it reads goes into valid content, and comments, conditional comments, `<style>`, `<script>` and `<head>` give none — except the children of a `<div data-pm-type>` naming a block atom (an `embed`), which a load (and a paste of rinch's own copy) reads as that atom and whose content (an app's export fallback) it drops; an unclosed one therefore ends the read. It is not a browser's rendering: no CSS is read (`display: none` text is read) and whitespace is not collapsed (#1406). Character references are the HTML standard's (#1415): 2125 names in `serialize/html_entities_table.rs`, generated from the standard's `entities.json` by `tools/gen_html_entities.py` (never edited by hand; about 29 KB of data, +31 KB on a 246 KB size-optimised wasm build of the reader), matched as the tokenizer matches them — with its `;` a name is the whole run of letters and digits, and the 106 legacy names also decode with no `;` as the longest one the run starts with (`&notit;` is `¬it;`), except in an attribute value before `=`, a letter or a digit (`?a=1&copy=2` stays). **A block-level element that holds no block ends the line before it** (#1413, `HtmlParser::end_line`): `a<div></div>b` is two paragraphs, where it read `ab`; such an element is a line itself when the text it holds directly is more than ASCII whitespace (a non-breaking space), and one that is empty or holds only collapsible whitespace directly is none (`<div> </div>` was a paragraph of one space; `<div><span> </span></div>` still is, where a browser shows no line). **An inline element that holds a block ends no line** (`read_children`): its children are read where it stands, with its mark in `Building::active` (inline content is parsed with those marks, blocks get them once through `push_blocks`), so `x<b>y<div>z</div>v</b>w` is `xy`, `z`, `vw` as in Chrome, where each part was a line of its own; a `<span style>` around blocks still carries no colour or highlight (#1462), so one with a stray `</p>` inside it now loses the colour main kept on its one fused line. A tag name runs to whitespace, `/` or `>` (the old tokenizer stopped reading at `<o:p>`'s colon, so a Word paste kept one paragraph); an element with no node or mark is read through, inline unless it holds a block; end tags are implied as a browser implies them; bare `<td>`/`<tr>` runs are a table and what has no place in a table goes in front of it; a mark around blocks leaves hard breaks bare; a `<div style="white-space: pre">` (VS Code) is a code block; the tree is at most 192 elements deep (`html_tree::MAX_DEPTH`), which bounds the reader's recursion: an element opened deeper stays open (its end tag is matched by name), but is flattened into the element at the limit — a block as a child of it, split around the blocks inside it (its attributes go with its first part that holds anything — moved, not copied a part, which was quadratic); an inline element as its content, its mark lost — so past the limit no text is lost and every block is still a line of its own; what goes is nesting (the first cut opened nothing past 128 and ran separate blocks' words together). Chrome's limit is 512 and it keeps every element too; 192 is what an unoptimized build reads on a 2 MB thread stack (about 6.4 KB of stack a level, 1.1 KB optimized; `the_depth_limit_reads_on_a_small_stack`), so a document nested deeper than that reads back from its own HTML as the same lines with less nesting. A tag finds the element it closes however many are open: it scans the innermost `MAX_SCAN` (192) and past those asks `open_at`, an index of where each tag name is open, about the names in `SCOPE_NAMES` (every special or foreign element — the only ones that are closed by implication, stop that, or bar an end tag), so the answer is the unbounded scan's at a fixed cost a tag. (Round 1 just stopped at 192, and with that many unclosed elements in a block its end tag ended nothing: `<h1>` + 250 `<u>` + `head</h1>body` was `headbody`.) Reading is linear in the input's size on every shape tried, and pinned by step count on the three that were not (many open elements, a block split past the limit, padding); mark elements nested directly in one another around blocks mark them once for each mark type (it was once a level: 192 `<b>` around a 2,000-row table read in 1.9 s unoptimised, now 51 ms); with a block-level element between each pair (95 × `<b><div>`) it is still once a level, as on main, linear in the rows and bounded by the depth limit. Not read: `<input>` / `<select>` values, embedded-content fallback, `<svg>`, `<math>` (an unclosed `<svg>`/`<math>` ends at the first HTML start tag the HTML parser ends foreign content at, so it no longer swallows the rest of the input; an unclosed `<select>` or `<object>` still does, where Chrome shows what follows), an `<img>` with an empty `src`; whitespace is not collapsed (#1406). Bare table parts that do not make full rows are padded with empty cells to a rectangle (`HtmlParser::pad_rows`), since a ragged table stalls a collaborating editor's outbound — **only when that takes at most 8 empty cells for each cell written** (16 whatever the number): a span claims slots without writing them (`<td colspan=1000>` over 65 one-cell rows asked for 64,935 cells from 1.2 KB), so past the bound the rows are left as written, ragged, and the grid is not even laid out when the spans cannot cover enough of it. A `<table>` is read as written and never padded; the reader makes no cell the markup did not write there, and its `colspan` is capped at 1000 as before. **A formatting element's end tag across an open block ends the element there** (#1410, `HtmlFragmentParser::end_under`; the HTML parser's fourteen formatting elements — `a`, `b`, `i`, `code`, `em`, `strong`, `u`, `s`, …): in `<b>a<div>b</b>c</div>d` `a` and `b` are bold and `c` and `d` are not, as a browser's adoption agency algorithm leaves them (the end tag was skipped, and the bold ran to the end of the input). The element's entry on the open-element stack becomes a placeholder that is spliced into its parent when it closes, and every element open above it gets a copy of the element around what it holds so far, so no path in the tree gets deeper; an inline element open inside the innermost block that is no formatting element ends too. The end tag is still skipped where Chrome skips it — out of a table cell, an `<object>`, `<marquee>` or `<select>`, a `<foreignObject>`/`<desc>` inside an open `<svg>`, with more than 7 blocks open in between (`MAX_ADOPT_BLOCKS`, Chrome 153's number), and for an element that is no formatting element (`<span>`, `<mark>`, `<sub>`) — and, which a browser does not do, with more than 32 elements of any kind open in between (`MAX_ADOPT`, what bounds one end tag's cost). Not done: a browser also opens a formatting element again after a block's end closed it (`<p><b>a</p>b` is two bold lines there, one here; #1445), and a second `<a>` inside an open one does not end the first. **A `</p>` with no `<p>` to close ends the line** (an empty `<p>` in a browser): `<p>a<ul>…</ul>c</p>d` puts `c` and `d` on two lines; it is an empty block that makes no paragraph, not an empty paragraph. Inline children of a list side by side are one item (`<ul><b>Aa</b>Bb<li>…` is `AaBb`, then the item), where each was an item; an inline element that holds a block still starts an item of its own there (#1446). Pins: `rinch-editor-core/tests/html_reader_1413.rs` (each expectation is Chrome 153's `innerText` lines and computed bold/italic for the same markup), `html_entities.rs`'s unit tests. **Code pasted in a line of text is a line each** (`fit::code_lines_as_blocks`, decided once for the range in `Transform::replace_range`, before any candidate): a slice open into a `NodeSpec::code` textblock, replacing a range that starts in a textblock that is not code and is **not exactly that textblock's whole content**, has that block turned into a paragraph per line first — the first continues the line, the text after the range joins the last; a one-line block is just text continuing the line. Otherwise a multi-line VS Code paste after `ab` was one paragraph holding raw `\n`, and at the *start* of a line with text the fit replaced the line with the code block and took the line's own text into it. A range that is exactly one textblock's whole content (an empty line, a line selected whole) takes the block as a block — one that starts at a line's start and ends in a later line does not (review of #1411, round 3: that range, and one copied line at the start of a line with text, still made the kept text code, or a heading holding line ends); a slice closed at its start lands whole; a code target takes the text. Pins: `rinch-editor-core/tests/html_reader_total_1397.rs` (generator + `reading_is_linear_in_the_input`, by step count), `html_reader_review_1411.rs` and `html_reader_review2_1411.rs` (depth, `<svg>`, padding and its bound, unclosed elements by the hundred, the flattening's step count, code at the start, middle and end of a line, the reviews' mutants), `html_reader_clipboard_samples.rs`, `replace_range.rs` (`code_lines_that_continue_a_line_of_text_are_a_line_each`), `rinch-editor-view/tests/html_reader_total_1397.rs`. **A cell selection is not a range** (`from()..to()` are the positions before its corner cells): `Transaction::replace_selection` refuses one, and the paste clears the cells (`table_ops::clear_cells`) and fits into the top-left one in the same transaction, as `insert_text` does. Bullet and ordered items join as siblings; a task list pasted in a plain item (or the reverse) nests, as in ProseMirror. **Pasted and dropped pictures: `EditorHandle::on_image_input(|ImageInput { source, bytes, mime, name, anchor }| -> Option<(src, alt)>)`** (desktop and web). `on_change` fires only for **local, document-changing** edits: `update` (which typing, paste and IME commit all funnel through), `command`, `insert_image`, and `toggle_link`. Those are the four `notify_change()` call sites in `rinch-editor-view/src/handle.rs`; if you add a fifth mutation path, it needs one too. It deliberately does **not** fire for selection-only changes, for `load_doc`/`load_html` (a programmatic load isn't a user edit — firing would make an autosave consumer immediately re-save what it just loaded), or for `collab_receive` (already in the shared CRDT). The callback runs with no internal borrow held, so it may re-enter the handle freely — e.g. call `doc()` to serialize for the save.

**Links are the app's; the pointer asks about the character under it** (`on_link_click` / `on_link_hover`). The editor never follows a link. `rinch_editor_core::link_at(doc, pos)` answers the link carrying the character **starting** at `pos` (content covering `pos..pos+1`) as a `LinkSpan { href, title, from, to }` over the whole run of adjacent content with the same `href`, across other marks. That is deliberately **not** `ResolvedPos::marks`, which answers what a *caret* would inherit: a link is non-inclusive, so a caret at either edge of it inherits no link, while the pointer over the link's first or last letter is on it. Desktop finds the character with `rinch_dom::text_query::cluster_range_at_point` (Parley's `Cluster::from_point_exact`, `None` beside a line's end) — never `byte_offset_from_position`, which answers the nearest caret boundary; the web takes "is there a link" from the browser's own hit test (`closest("a[data-pm-mark='link']")`) and "which character" from the caret-from-point boundary plus that element's `href` (`event_delegation::caret_point_from_point`, the one place rinch-web asks the browser for a caret under a point: `caretRangeFromPoint` where it exists, the standard `caretPositionFromPoint` otherwise — Firefox has only the latter, and a press there placed no caret before #1449; the standard path is tested by hiding the old call in Chrome 153, where the two agree on every point measured, and has not run in Firefox, #1461). A press is offered in `try_new_editor_click` / `handle_mousedown` before the caret moves, only for `click_count == 1` / `detail <= 1`, never for the context press or a leaf; a claimed one returns after focus with nothing else touched. Hover: `registry::set_link_hover(doc, Some((handle, hover)) | None)` keeps the one hovered link per document and fires callbacks only on a change, with no borrow held; `registry::link_hover_wanted()` (a thread-local count of editors with a hover callback, decremented in `EditorCore`'s `Drop`) gates all of it, so a pointer move pays one `Cell` read when no app asked, and desktop reuses the move's shared hit (`move_hit`, #881), called last in the hover arm because the callbacks are app code. The web decides a click's default action on an `a[href]` inside `[data-pm-editor]` in `handle_link_click` (a cancelled `mousedown` does not cancel the click's navigation): prevented when the editor is **editable** or has an `on_link_click` callback, native in a **read-only** editor without one; a `click` with `detail == 0` (Enter on the focused link, which is a Tab stop) is first offered to `on_link_click`, found from the anchor element (`link_of_anchor`), and a non-link-mark anchor is never offered. **Unmount is silent** (#147/#183): `EditorHandle::mount` releases its registration in `scope.on_cleanup`, and `unregister_editor` drops any `LINK_HOVER` entry the editor held without calling back, which also releases its `link_hover_wanted` count at the unmount. Neither callback runs inside a `batch()` (like `on_change`). **Margin anchors and the overlay slot** (#1677; guide: `contenteditable.md#margin-anchors-drawing-beside-a-line`). `EditorHandle::set_margin_anchors(Vec<MarginAnchor>)` replaces the set; `MarginAnchor { key, at: MarginAt }` is `MarginAt::Pos { pos, assoc: MarginAssoc }` (carried by local mappings in `commit` and by `RemoteCarry` in `carry_anchors_remote`, both through `margins::Margins`; lost by a load or a peer splitting/joining/retyping its block) or `MarginAt::Sticky(bytes)` (`collaboration`: resolved each pass with one `CollabSession::locate_sticky_many`, #1676). `on_margin_layout(|&[MarginLine { key, top, height }]|)` is a `Hook` (owner-checked, no borrow held) called by `EditorHandle::margin_pass` only when the report — lines, or `margin_text_right()` (the first laid-out top-level block's right edge) — changed. `registry::update_all_carets` runs every editor's margin pass **before** any caret pass (the overlays' writes would read as pending layout), and returns `true` when a callback ran. Coordinates are the overlays' frame: the container's padding box, unscrolled (`RinchDomEditorView::measure_lines`: `block_offset_in_container` plus `DomDocument::query_line_box`, the new trait method — rinch-dom answers the Parley line the caret is drawn on, `text_query::line_box_for_offset`, so an anchor beside a tall picture or in a `<sub>` reports the line, not its glyph box; the web rebuilds it from what is on the caret's line — every text run's client rect overlapping the caret's line by more than half, grown (or shrunk) to **its own element's** computed `line-height` with the smaller half-leading (whole px) above as Chrome splits it, and every `img`/node-view host's box — so a line a tall picture makes taller is reported whole, and a `sup`/`sub`/big `code` run under a unitless line-height matches Chrome 155; `query_line_boxes` (new, defaulted to one `query_line_box` each) answers all of a block's carets from one read of its text, so 500 anchors in one 400-line paragraph cost 32 ms a keystroke in release, not 259; default `None`, then the caret rect grown to `line_box_height`); boxes that overlap in one textblock are merged, so anchors on one line report one box; before a leaf block, that block's box. A pass while `DomDocument::layout_pending()` (new; rinch-dom: `styles_dirty || layout_dirty || ifc_dirty || dirty_ifc_text_roots`; web and default `false`) measures nothing and owes itself again, so the desktop pass a key runs before its layout cannot report a line about to move. Idle (`Margins::is_idle`: no anchors, nothing reported, nothing watched) the pass is one `try_borrow`; `__margin_counters()` (doc-hidden, `(passes, anchors measured)`) pins that. A pass whose `RinchDomEditorView::margin_key` — for every block an anchor is measured on (`margin_target`), its offset in the container (summed up the chain, so a table cell's paragraph that moves inside a still table is seen), box, padding and border, and `DomDocument::text_layout_generation(block)` (new; rinch-dom's per-node stamp `NodeTree::text_layout_stamps`, written at the two places a text layout is built; web/default `None`), plus the first block's box, for the same document — equals the last measure's measures nothing, and the anchors' positions are reused while the document is the same `Rc`: a layout of anything else (a spinner, a hover, a label's text, another editor's keystroke on the web) costs that key, not `N` measures. On the web, with no stamps, a rewrap that moves no anchored block's box is seen at the next change that does. `EditorHandle::mount` owes a pass when anchors and a callback are set, so anchors set before the mount, or kept across a re-mount, report on the web too; `set_margin_anchors` owes one only when a callback listens. A document change owes an overlay pass while anchors listen (`margins_wanted`, local and remote), and while anchors are set the container is handed to `registry::notify_node_view_host`, which on the web adds it to the node-view `ResizeObserver` (a resize that rewraps reports). **`Editor { … children }`**: the children go in a 0×0 layer (`OVERLAY_SLOT_ATTR` = `data-pm-overlay`, inline `position: absolute; left: 0; top: 0`, `z-index: 2`, no `pointer-events`) appended to the container after mount; it also carries `NODE_VIEW_ATTR`, so every existing "an app's subtree inside the editor" rule — desktop `in_node_view`, web `editor_owning`, the caret map's skips, `offer_node_view_key` (no slot: falls through) — makes a press or key there the child's. Pins: `rinch/src/app/editor_margin_anchors_1677_tests.rs`, `rinch-editor-view/src/margins_tests.rs`, `rinch-web/tests/editor_margin_anchors_1677.rs` (Chrome 155).

**Read-only refuses edits in `EditorCore::commit`, and nowhere else.** `set_read_only(true)` makes the editor what `readonly` makes an `<input>`: caret, selection, `selectAll`, copy and every query work; every local change to the document does not — typing, IME commit, paste, cut, every document-changing `command` (so every key bound to one, and `undo`/`redo`), `toggle_link`, `insert_image`, a task-checkbox click, any `update` transaction that changes the document or sets stored marks. Each answers `false`. `can_run` never runs a command's dispatch branch (#834): editable, it is `EditorState::can_run` (`cmd(state, None)`); locked, it is `false` unless the command's plugin declared it selection-only (`Plugin::selection_commands`, aggregated into `Config::selection_commands` by `EditorState::create`, the plugin that wins a name owning its declaration; read by `EditorState::is_selection_command`), and then `cmd(state, None)`. It used to run `run_mapped` and ask `refuses` of the result — a full transaction build, apply and plugin fold per query, and an app command's dispatch-branch side effect firing from a toolbar. The declaration steers only the query; `commit` still judges a declared command that edits. Pins: `rinch-editor-view/tests/can_run_dry_run_834.rs`. The rule (`EditorCore::refuses`) reads the `prev`/`next` states rather than the caller, and `commit` is the single landing spot for a local change **that arrives as a transaction**, so **a new input path is read-only by default — do not add an `is_read_only()` check to an input handler to refuse an edit it already refuses.** (The one thing `commit` cannot judge from the states is a whole-document `load_doc`, which it is told about by `mapping: None`; a future mapping-less local change that is *not* a load would need an explicit origin instead.)

**A collaboration freeze refuses in the same place** (`EditorCore::locked` = the switch or `CollabSession::is_frozen`, read by `refuses`, `can_run` and `ime_set_preedit`): while the shared document holds a table too large to read, every local change is refused exactly as above. It is not the switch — `is_read_only()` still answers the switch alone — but the places below ask **`EditorHandle::refuses_edits()`** (read-only **or** frozen), so a frozen editor behaves as a `readonly` field everywhere: the OS input method off, Cut and Paste greyed, no quiet-Copy Cut, no clipboard read, and on the web the capture `<textarea>` `readonly` with printable keys still owned (measured in Chrome 153, `rinch-web/tests/rv6_frozen_keys.rs`). `collab_delete_oversized_table` requests an overlay refresh, which is what re-reads the web field's `readonly` once the freeze lifts; a read-only editor's `collab_delete_oversized_table` refuses (`Ok(false)`), as its loads do. The flag is read in these other places (and the Tab sites of #833, below), and every one is there for something a refusal **cannot express** — none of them refuses an edit:
`ime_set_preedit` (handle.rs) shows no composition, since its commit is refused; `attach` re-stamps the container on a re-mount. Desktop turns the **OS input method off** (`focus.rs`), greys **Cut and Paste** in the built-in context menu (`text_context_menu.rs`), keeps **Cut from becoming a quiet Copy** (`editor_cut`) and starts **no clipboard read** for a paste that cannot land (`dispatch_editor_paste` — a read is a 4s worst case and a permission prompt on some platforms). The web makes the capture `<textarea>` **`readonly`** so no soft keyboard rises (`sync_capture_read_only`), makes `cut` a no-op, and **keeps ownership of a printable key** while the capture textarea holds focus (`editor_input.rs`, `handle.insert_text(&key) || handle.refuses_edits()`; the editor owns no key at all once focus leaves that textarea, #271) — that last one looks exactly like the check the rule forbids and is not: without it Space scrolls the page and a letter reaches the page's own shortcuts. `collab_receive` never goes through `commit` — a remote change must not be recorded back onto the CRDT — so a read-only editor keeps integrating peers' deltas **by construction**; never gate `integrate_remote`, and never toggle the flag around it. While read-only nothing is recorded or broadcast, which is why `load_doc`/`load_html` are refused on a **collaborating** read-only editor (a load with a session attached is a write to the shared document) and allowed otherwise (the app showing a document is not the user editing one). The flag lives on the handle, not the view: it works before mount and survives a re-mount; the container carries `data-pm-readonly="true"` while it is on. **Tab is a key-ownership decision too, not a refusal** (#833): the keymap's `Tab`/`Shift-Tab` (sink/lift a list item) are consumed on a binding match whether or not they applied, which made a read-only editor a keyboard trap. When `refuses_edits()`, a plain Tab/Shift+Tab (no Ctrl/Alt/Meta) skips table cell-nav and the keymap, after the app's `on_key` has had it: desktop's Editor arm of the key routing calls `handle_tab`, which anchors a `FocusTarget::Editor` claim on the container (so a focus by `EditorHandle::focus`, with no DOM focused node, still starts from the editor's place); the web's `handle_keydown` calls `event_delegation::tab_from_editor`, which walks from the **container**, not from the capture textarea at the end of `<body>` — inside the trap that encloses it with the trap's wrap (`move_tab`, `handle_trapped_tab`'s arithmetic made start-anchored), otherwise over the document without wrapping. Past the last stop the key is left to the browser, whose Tab from the capture textarea leaves the page as from a native last control; before the first, the browser's Shift+Tab from that textarea would land on the page's *last* control (a wrap, where a native `<textarea readonly>` sends the focus to the document — trusted keys, Chrome 155, review of #2001), so `handle_keydown` blurs the capture textarea (`blur_editor`) and consumes the key (`rinch-web/tests/editor_read_only_tab_833.rs`, `rinch/src/app/editor_read_only_tab_833_tests.rs`). An editable editor has no built-in way out by keyboard; `on_key` is the app's.

**Caret affinity at a soft wrap is view state beside the selection** (#301). The end of one visual line and the start of the next are one model `Pos`, so `EditorCore` keeps `caret_hint: Option<(Selection, CaretAffinity)>` (`rinch_core::dom::CaretAffinity`, `Downstream` by default — the lower line's start — or `Upstream`, the upper line's end). It applies **only while the selection equals the stored one**, so every other writer (typing, undo, a load) retires it without knowing it exists, and a plain `set_selection` clears it explicitly, even to the same caret. A **document** change — a local `commit` or a remote integrate — carries it to the new selection when it only *shifted* it (`EditorCore::carry_caret_hint`: both ends moved by one amount, the head at the same offset in a textblock of the same type and attrs whose content **up to the head** is unchanged), as CodeMirror maps `assoc`: a peer typing in an earlier paragraph, or after the caret in its own, leaves an upstream caret at the end of its line; an edit before the caret in its own block drops it, and so does a commit landing any selection other than the hinted one (no revival by another route). Right before a `hard_break` the caret is always `Upstream` (`EditorCore::affinity_at`): the break has no bytes in the host text, so the positions before and after it share one offset, and the model says which line each belongs to. The test is positional, not the transaction's mapping, because a remote integration rebuilds the document and has none. `EditorHandle::set_selection_with_affinity` stores it **before** the dispatch (so `on_selection_change` — where a popup reads `caret_rect(head)` — already sees it; inert unless that selection lands) and owes an overlay pass when only the side changed; `caret_affinity()` / `caret_affinity_at(pos)` read it; `caret_rect` at the head and the caret overlay draw with it, through `DomDocument::query_caret_rect_with_affinity` / `query_caret_position_with_affinity` (trait defaults: the affinity-blind answer, so the mock keeps compiling). rinch-dom hands it to `parley::Cursor`; the web draws `Upstream` as the collapsed range (Chrome draws a wrap point at the upper line's end) and `Downstream` at the start edge of the character after it (its right edge in a right-to-left run). The affinity-blind `query_caret_rect` / `query_caret_position` answer `Downstream` on both backends. Setters, identical on both backends: End sets `Upstream` when its edge is a soft wrap point (the line's end, after any hanging space — desktop reads the line the caret is drawn on from its Parley layout, `text_query::visual_line_range`, with no hit test, so a line scrolled out of view answers too, #1107); a press and an Up/Down hit set `Upstream` when the upstream caret is nearer the hit's y than the downstream one (`editor_hit_affinity` / web `hit_affinity`; nearness, not containment — a caret rect covers the glyphs, not the line box, and Up/Down probes 1.5 caret heights down, which on a short-caret face lands in the leading: CI's did); Home and the rest are `Downstream`. Desktop Up/Down within one textblock step by Parley **line index**, never by a y coordinate (`RinchApp::line_step_in_textblock`: the caret's own line ±1, the goal column resolved on that line as a press would be — `text_query::caret_on_line`, images and their halves included — and the side of a soft wrap that is on it; no hit test), so a line scrolled out of view answers too and the caret is then scrolled into view, as in Chrome 155 (#1121); only a step off the textblock's first or last line, or one whose answer is drawn on neither side of the target line, hit-tests. A caret's line (`text_query::line_index_of`, behind Home, End and `query_line_box` too) is the line of the cluster `Cursor::geometry` draws it from, read as an index: line boxes overlap and need not start in order (an image on a baseline reaches past the next line's top; a 72px span in 24px lines starts above the line before it; a `line-height` below the font's overlaps every line), so a rule on `block_min_coord` named the wrong line, and Down skipped lines or stuck. The visual-line motions measure from the head's affinity-aware rect, so Home/End, the web's soft-line deletes and Up/Down follow it. Desktop's End no longer steps back one position (on an `overflow-wrap` glyph wrap that stopped before the line's last letter). The desktop `<textarea>` keeps a caret affinity of its own since #941, the same `CaretAffinity` over the same Parley path: ArrowUp/ArrowDown landing on a soft-wrapped line's end and End go to the wrap point (after any hung space) as `Upstream`, written as `data-cursor-affinity="upstream"` beside `data-cursor-pos` by the sync that moved the caret (`RinchApp::pending_input_caret_affinity`; every other sync removes it, so a click, a horizontal arrow or an edit is `Downstream`); paint, the next vertical move / Home / End and the Android toolbar anchor read it (`rinch_dom::form_control::caret_affinity`). A click is still `Downstream` (a press right of a wrapped line's end draws its caret on the next line, #1617). Not the selection-rect slivers (#1010). Pins: `rinch/src/app/editor_caret_affinity_tests.rs`, `rinch-web/tests/editor_soft_line.rs` (+ `_review.rs`, Chrome 153's answers), `handle.rs` `tests::caret_affinity`.

**A caret beside a padded mark is drawn on the side its marks say** (#1426, part 2). A mark wrapper's horizontal padding, border and margin take room on its line (`ifc::EDGE_BOX`, part 1) but hold no flat bytes, so at a run boundary one byte names both sides of the padding, and Parley draws the byte's caret before every edge box at it (at a line's start, after a start box). The view asks `RinchDomEditorView::mark_edges_beside`: past the end edge of each wrapper of the run before the caret whose mark the caret does not carry, and past the start edge of each wrapper of the run after it whose mark it does carry (`ResolvedPos::marks`: an inclusive mark such as `code` or `highlight` continues past its end, a link does not), the last such edge in logical order winning; `DomDocument::query_inline_edge_caret` / `_rect` answer the caret past one edge (rinch-dom: the edge box's trailing side; default `None`, so the byte's caret stands). So the caret after inline code stays inside the pill and the caret after a padded link is drawn past its padding, where typed text goes, on desktop. Not on the web: the browser draws the caret at the DOM position the byte maps to. A wrapper two runs share (#1833, below) has no edge at their seam, so `mark_edges_beside` offers only the wrappers that end or start there. Pins: `rinch/src/app/editor_mark_edge_caret_1426_tests.rs`, `editor_shared_mark_wrappers_1833_tests.rs`.

**CSS generated content holds host bytes the model does not** (#891). rinch-dom lays a `::before`/`::after`'s text out in its textblock's IFC (a pseudo-element box is a `<span>` whose only child is its text, `style_resolution/pseudo.rs`), so it takes bytes of the flat offsets every text query reads; the browser's DOM ranges never count it. `DomDocument::generated_flat_ranges(block)` (default none; rinch-dom: the IFC text ranges whose text node's parent `is_pseudo_element`, a list marker counting as a `::before`) names them, and the view maps through them in the three places it turns model offsets into host bytes and back: `caret_target` and `selection_targets` with `host_flat_byte` (a stretch that starts at the byte is passed for a `::before`, which belongs to what follows it, kept for an `::after`), `pos_at` with `model_flat_byte` (a byte inside generated text is the byte it stands at). Everything that reads Parley by `caret_address`/`pos_at` (the vertical motions, Home/End, link hover) is in host bytes already. At a mark's edge the marks pick the side, as for #1426's padding: rinch-dom's `query_inline_edge_caret` counts the element's own generated text as part of that edge — the inner side of the end edge is before its `::after` text, the outer side past the edge box or, with none, past the text (mirrored for a start edge and its `::before`) — so the caret right after a link with an arrow is drawn past the arrow and the caret at the end of an inclusive bold run before its `::after`. rinch-dom's `query_selection_rects(_with_boxes)` cut generated text out of the highlight (`RinchDocument::cut_generated`). The web needs none of it: its byte walks count DOM text nodes only, and it draws the caret at the DOM position (its selection highlight is the `Range`'s client rects, not checked against generated content). Pins: `rinch/src/app/editor_generated_content_891_tests.rs`, `view.rs` `tests::generated_flat_ranges_are_stepped_over_both_ways`.

**Adjacent runs share the wrapper of a mark that continues across them** (#1833, Joe's option C). `ViewDesc::regroup_inline` walks a textblock's inline children with a stack of open wrappers: a run keeps every open wrapper, from the outside in, whose mark it also carries, closes the rest, and opens its other marks inside them (the last in canonical type-name order outermost, the nesting a run alone always had). So inline code split by bold, italic or a link is one `<code>` and one pill on both backends, where each run had a wrapper chain of its own (two pills once #1426 gave inline padding room). A run's nesting depends on the runs before it and can differ from the copy-out HTML's, which nests each run alone (`slice_to_html` reads the model, not the view). A run's chain is `ViewDesc::wraps`; the textblock keeps its wrappers in `inline_wrappers`, reuses a run's own wrapper for the same mark before making one, moves only nodes not already in place (`place_children`) and discards wrappers no run uses. It runs only when `diff_children` reports a structural change (a child built, replaced, removed or moved; a run whose mark set changed is rebuilt, as before, so its new node goes into a new wrapper while that wrapper is detached); the children the diff dropped are retired after their successors are placed (an emptied block would restyle under an `:empty` rule); a keystroke inside a run is one text write, the same host work as in an unmarked paragraph (`shared_wraps_1833_tests::typing_at_a_shared_seam_writes_only_the_text`). Decoration segments stay per run, inside its wrappers; a hit on a shared wrapper's own box resolves to its first run (`find_node_by_host`). A root whose node is itself a textblock (`doc: text*`) is regrouped like any textblock, at mount and on update. The caret at a seam inside a shared wrapper, with stored marks that leave the wrapper's mark out (code toggled off), is drawn past that wrapper's end-edge width (`RinchDomEditorView::shared_wrappers_left`), where the typed character lands once the wrapper splits; the same toggle inside one run still draws the byte's caret, as before #1833. Pins: `rinch-editor-view/src/shared_wraps_1833_tests.rs`, `inline_doc_1833_tests.rs`, `incremental_fresh_1833_prop_tests.rs` and `tests/incremental_fresh_handles_1833.rs` (random edits, undo/redo, decorations, node views and a collaboration guest: incremental DOM == a fresh render; `RINCH_PROP_SEEDS` raises the seed count), `rinch/src/app/editor_shared_mark_wrappers_1833_tests.rs`, `rinch-web/tests/editor_shared_mark_wrappers_1833.rs` (Chrome 155; Firefox checked locally).

**Scrolling the caret into view is decided on the handle, from what changed the state — never from the caret's geometry** (#837). `EditorCore` carries a `ScrollGate` (ProseMirror's `tr.scrollIntoView()`): `commit` arms it for a **local** change that altered the selection or the document, and `EditorHandle::update_caret` fulfils it — a `NodeHandle::scroll_into_view()` on the view's `scroll_anchor()` (the caret, a node outline, a cell selection's head-cell wash) — on the first caret pass that **has** an anchor, so an Enter into a not-yet-measured paragraph still scrolls once it is laid out. It is **not** armed by focus (#846's review): a press that places the caret arms through `set_selection` anyway, and one that does not (a task checkbox, a right-click on an image) must not jump to the old caret — nor does `EditorHandle::focus()`, which arms nothing (giving the keyboard back after a dialog must not jump either); an app that wants something on screen asks with `scroll_into_view`. **But focus performs a scroll already owed**: only the focused editor's caret pass fulfils the gate, so a `set_selection` of a caret on a blurred editor stays armed until the next `focus()` (#922's review, D4 — the deep-link `set_selection(caret); focus()` relies on it; pinned by `focus_performs_a_caret_scroll_already_owed_and_arms_none`). It is **not** armed by `collab_receive` (no `commit`), `load_doc`/`load_html`, a read-only refusal (the arm sits after `refuses`), or a public `update(..)` transaction that does not call `tr.set_selection` — that one is the shape of an app's or a peer's edit elsewhere, which maps the caret. The handle's own input paths (`insert_text`, `set_selection`, paste, `ime_delete_surrounding`) go through the private `dispatch(.., input: true)` and arm whenever the selection or document changed. The view's `ViewRequest::ScrollSelectionIntoView` still says "the overlay moved" and the handle reads it for nothing else: #837's first cut gated on it, and its review measured it pulling a user who had scrolled away back to the caret on a resize reflow, a remote edit above the caret, and every scroll of a virtualized editor (whose blocks move as they are measured). A non-empty text range drops an owed scroll (a Shift+arrow head is not revealed). Desktop applies the scroll after layout and moves only the **nearest** scroll container; the web calls `scrollIntoView({block: "nearest", inline: "nearest"})` at once, which moves every scrollable ancestor (**#842**) — and that makes `NodeHandle::scroll_into_view` live on `rinch-web` for any caller, where it used to be the trait's no-op. **A caret moved into a block of a virtualized desktop editor that is collapsed** (Ctrl+End from the top, a `set_selection` far below) has no anchor, and the window follows the scroll position, which is what the owed scroll is waiting to change — so it used to never scroll (#845). `virtualization::pre_layout` now materializes the focused editor's caret block while `EditorHandle::caret_scroll_owed()` (the gate is armed), as it does for a pending reveal; the caret pass then scrolls to the block where the **estimated** heights above it put it. The window moves there and measures those blocks, which moves the caret, so that frame's window entry carries a `follow` flag (set in `pre_layout`, cleared by the next frame's `pre_layout`): in each `post_layout` of the frame — the frame's layout pass and every bounds-settle pass after it (`settle_bounds_writes`, at most `BOUNDS_SETTLE_PASSES`, each run only while the layout is dirty) — it calls `EditorHandle::owe_caret_scroll()`, and the caret pass right after follows the caret (a no-op once it is in view). Those passes bound the corrections; a window still moving after the last one is not followed into the next frame, and in every case built so far the caret is in view within the frame. Because the follow ends with its frame, a user scroll after it — even a wheel event right after that frame — is left alone. The follow does not start while a `scroll_into_view` is pending (`pending_reveal_range()`): the caret pass runs the caret scroll before the reveal, so the reveal decides where the view goes, as it does without the caret move (#2019's review, F1: following the caret had pulled a deep link thousands of px past its range's start). Known limits: a wheel scroll in the **same** event batch as the caret move, before that frame, is undone by it; and a caret move inside a block that is already laid out but sits below unmeasured blocks (an arrow key in a deep link's caret block) is scrolled by the input path's caret pass before any frame, so it is never owed at `pre_layout` and not followed (F3). It needs a frame to run: from app code the selection change owes an overlay pass, and the input paths request a redraw. Pins: the handle's `ScrollGate` tests, `rinch/src/app/editor_scroll_gate_tests.rs`, `rinch/src/app/editor_virtualized_caret_scroll_845_tests.rs`, and `rinch-web/tests/editor_scroll_into_view.rs` (run it `--features collaboration` too). Guide: `docs/src/guide/contenteditable.md#keeping-the-caret-in-view`.

**Programmatic focus and reveal: `EditorHandle::focus`, `EditorHandle::scroll_into_view`** (a followed deep link: `set_selection(range)`, `scroll_into_view(from, to)`, `focus()`; guide: `contenteditable.md#focus-and-scrolling-from-code`). `blur()` is its other half (`registry::set_blur_handler`): the web registers `editor_input::blur_editor` (only if that editor is the focused one: blur the capture textarea if it is `activeElement`, release the editor, `refresh_caret`); desktop registers none, so the handle calls `rinch_core::post_release_request(doc_key, container)`, a channel beside the single `FocusRequest` slot that a `focus()` never discards and that never discards one; `RinchApp::drain_focus_requests` (every drain point) takes both with `take_pending_focus_steps` and applies them **in posting order** (`blur_node` for a release: a no-op unless that node still holds the keyboard), and when the parked request needs a layout the releases around it wait with it. Review of #1481: `blur()` calls `flush_pending_effects()` first (program order: `open.set(false); editor.blur()` releases after the closing overlay's focus restore); `handle_event` runs `drain_focus_requests(false)` before routing a `KeyDown`, `Ime` or `MouseDown`, so focus work parked by an `on_key`/`oninput`/interceptor/menu-shortcut handler (a `focus()` too) is applied before the next queued key, not at `AboutToWait`; the web blurs the textarea **before** `set_focused_editor(None)`, so the browser's `compositionend` inside the focus change still finds the editor and commits; and desktop's `FocusTarget::Editor` teardown calls `ime_clear_preedit()` beside `hide_overlays()` — the `Ime(Disabled)` that follows is routed by the new owner, so a preedit used to come back on the next focus after **any** blur (dropped, where an `<input>` commits). Pins: `rinch/src/app/editor_blur_tests.rs`, `rinch/src/app/review_1481_probe_tests.rs`, `rinch-web/tests/editor_blur.rs`, `rinch-web/tests/review_1481_probes.rs`, `review_1481_modal.rs`, `rinch-core` `events::selection::tests`. `focus()` asks the platform through `registry::set_focus_handler`: the web registers one (`editor_input::focus_editor`, the focusing half of `handle_mousedown` — focused editor, capture textarea focused with `preventScroll`, `refresh_caret`); desktop registers none, so the handle calls `NodeHandle::focus` on its container, which posts the ordinary focus request, and `RinchApp::try_focus_input` maps a registered editor container to `FocusTarget::Editor` (so `NodeHandle::focus` on a container works on desktop too). `scroll_into_view` stores the range on `EditorCore::reveal` (carried through local commits by `carry_reveal`, dropped by a load, replaced by a later call), marks the document in `registry::reveal_owed` and runs `request_overlay_refresh`; `update_all_carets` then calls `EditorHandle::reveal_pass` for **every** editor, focused or not, after the caret pass, which places two hidden `data-pm-reveal` probes (`RinchDomEditorView::position_reveal`: 1px wide, the caret line grown by `REVEAL_MARGIN` = 16px, clamped to the container top and the last block's bottom) over the end and then the start and calls `NodeHandle::scroll_into_view` on them in that order — two `nearest` scrolls leave the start visible whichever side the range was on, which one box around a range taller than the scroller would not. The reveal waits on the handle until a pass has geometry for its **start**; the end is revealed with it if it has geometry too, and otherwise the start alone (#922's review, D3: a virtualized range whose end block stayed collapsed used to stay pending for good). A pending reveal is dropped after `REVEAL_PATIENCE` (8) consecutive passes with no geometry for its start (`reveal_misses`, reset per request); a `display: none` editor has no laid-out text since #509/#826 (a hidden subtree is not an IFC), so it answers no geometry for its start and its reveal waits, and is fulfilled once the editor is shown — unless `REVEAL_PATIENCE` passes go by first, which drops it. Desktop folds `registry::overlay_pass_owed` (`reveal_owed` is its old name, kept as an alias) into `has_dirty_nodes`/`has_pending_layout` and the resolve short-circuit, so a request from an effect or timer wakes one resolve; the pass clears the flag fulfilled or not, so an unfulfillable reveal never spins frames. **A selection change owes the same pass** (#1001): `EditorCore::commit` calls `registry::owe_overlay_pass` whenever the selection moved, because a selection-only transaction dirties no DOM and a `set_selection` / `command("selectAll")` from a toolbar, timer or effect otherwise drew no caret or highlight until something else laid out. The input paths run `refresh_editor_overlays` right after their edit, which clears it in the same turn. The web has no frame loop to ask, so it registers `registry::set_overlay_pass_scheduler`: the first owe queues a microtask that runs `refresh_caret` only if a pass is still owed (`any_overlay_pass_owed`) — a keystroke pays one empty microtask. **Inherited marks follow ProseMirror's `inclusive`.** `MarkSpec::inclusive` (default `true`; `MarkSpecBuilder::inclusive(false)`) decides whether a mark carries on past its end. `ResolvedPos::marks` — which `marks_at`, `Transaction::insert_text` (so typing, IME commit and every other text-entry path), `add_stored_mark` and `is_mark_active` all read — gives the run's own marks inside a run, the marks of the run *before* a boundary, and the run after at a textblock's start; a non-inclusive mark is dropped at a boundary unless the run after carries a mark of the same type (ProseMirror asks for the same attrs; see the seam note below), and at a textblock's start. The starter kit's `link` is non-inclusive (every other mark is inclusive), so text typed right after a link is plain, and a caret at a link's start or end reports no link — except at the seam of two different links, where both continue the first (below). The collab projection resyncs a non-inclusive mark **per char**, as it does `@atom` (below): yrs puts an insert at a range's end inside the range, and a per-span clear-and-rewrite of the link would revert a peer's concurrent change to it. A char typed right after one is **inserted with its attributes** (`splice_min_with_marks`, yrs `insert_with_attributes`) when it carries exactly what the char after it carries (`inserts_after_non_inclusive`): the insert then walks past every formatting marker between the two and writes none, so a peer's concurrent extension of the link, or link over the following text, survives (review of #901, D2 — insert-then-clear's `format(X, link: null)` deleted the end marker those depended on). **Any other shape takes insert-then-clear**, because there `insert_with_attributes` stops at the first mismatching marker and writes `{link:null} X {link:old}` — and that trailing restore brings a peer's concurrently *removed* link back over the following text (round 2, F1/F2: a bold link; an image after the link). **The yrs API cannot express "plain X between two different links" without such a restore** (every write that changes a key's value writes a restore after it unless the next item already matches, and `format` deletes every same-key marker up to the next char), so `ResolvedPos::marks` departs from ProseMirror at that seam: typed text continues the first link and needs no marker (round 2, F3/F4). **Known limitation, pinned (#923):** a peer's concurrent href change or adjacent link can take the typed char in (an href change in one client-id order, a link over the following text in both) — nobody's edit lost, convergent. Not for atoms: a literal U+FFFC absorbed that way reads back as a second image. **Inline decorations** (#836). A plugin's `decorations()` may return `Decoration::inline(from, to, attrs)` as well as widgets: the view splits the covered text into `<span data-pm-deco class=…>` segments (an undecorated run stays a bare text node) and re-syncs them on every transaction. The core does **not** remap a decoration set — `EditorState::decorations()` asks every plugin afresh, so a plugin that caches ranges maps them itself through `tr.mapping()` in `Plugin::apply`. The stylesheet ships `pm-spell-error` / `pm-grammar-error` as wavy underlines, which rinch-dom paints natively (`text-decoration-style: wavy`; the other styles parse and paint solid). The editor ships its own default light/dark stylesheet (`rinch-editor-view/src/styles.rs`, injected once by the view); toggle dark mode with `handle.set_dark_mode(true)` (sets `data-pm-theme="dark"` on the container). Don't hand-roll editor CSS.

### Collaboration (optional, opt-in — M9)

Real-time collaborative editing is a feature-gated adapter, **not** part of the model. The pure `rinch-editor-core` model stays renderer- and CRDT-agnostic; `rinch-editor-collab` projects it onto a **yrs 0.27** (Yjs) CRDT so concurrent edits converge, then translates remote CRDT changes back into editor `Step`s. This crate is the **only** thing in the workspace that links a CRDT engine (yrs replaced Automerge in issue #190).

It is gated behind the optional `collaboration` feature (which implies `desktop`, since the editor wiring lives there), so **default builds — desktop AND web — link zero CRDT code**. The adapter itself is pure model↔CRDT logic with no platform deps and is **wasm-compatible with no shims** — yrs carries its own `fastrand/js` randomness source and builds for `wasm32-unknown-unknown` with no extra features — so a future Rust web editor view can reuse this *same* adapter rather than bridging to a separate JS CRDT.

Enable with `features = ["collaboration"]` on the `rinch` facade (or depend on `rinch-editor-collab` directly).

The design rests on one invariant — **`model ≡ project(model)`**: every local step is projected onto the CRDT, every remote CRDT change is rebuilt into the model. Convergence then follows from yrs's own convergence.

**Staged scope (design A22):** the first milestone covers **flat text-blocks + marks** (`paragraph`/`heading`/`code_block` with text + bold/italic/link/… marks), the **containers** `bullet_list`/`ordered_list`/`list_item` and `blockquote` (nested into each other and around text-blocks to any depth), **tables** (`table`/`table_row`/`table_cell`/`table_header_cell`, spans included, whose cells tile their grid), the **leaf block atoms** `horizontal_rule` and `embed` (a block with no content of its own, projected as a block with empty text; since #836, `embed` since node views part A) and the **inline atoms** (`image`/`hard_break` — one U+FFFC char of the block's text carrying a reserved `@atom` formatting attribute that names the node type and its attrs). Anything else — `task_list`/`task_item`, a ragged table — is `CollabError::Unsupported`: the adapter **fails loud** rather than silently dropping a change (a silent drop would reintroduce the exact divergence class the editor rewrite killed).

**`horizontal_rule` in scope is a wire change that needs a coordinated upgrade.** The format tag did not move (a rule needs no wire shape of its own), so a peer built before #836 accepts the bytes and then refuses the rule on read — `Unsupported`, which **poisons its session** (#196). Loud, not silent, but every peer sharing a document (PlotWeb's included) must be on a build with leaf atoms in scope before any of them inserts a scene break.

**`embed` is the same kind of change** (node views, part A): an older peer's starter kit has no `embed`, so it refuses one on read (`Unsupported`, "unknown block type `embed`"), a join from a snapshot holding one fails, and a live older peer is poisoned for as long as an embed is in the shared document (it heals when the last one is deleted). Every peer must run a build with `embed` before any of them inserts one.

**`blockquote` is the same kind of change too.** A quote is a container exactly as a list is (a node with a `content` array), so the format tag did not move, and a peer built before quotes were in scope refuses the type on read: joining from a snapshot that holds a quote fails, and a live older peer that integrates one is poisoned for as long as the CRDT holds a quote — which can be the document's whole life: a quote emptied by concurrent deletions is **void**, shown by no upgraded peer and deleted by none (it stays inert so a third peer's concurrent insert can still land in it), so an older peer refuses it for good (measured by #1229's review). A local edit reads back only the blocks it changed while the top level holds no void container (`CollabDoc::top_void`, recomputed only when foreign bytes arrive, since only a merge can leave one); with one present it pays one shape read per top-level block to find each visible block's raw index. Pins: `tests/projection_cost.rs` (CRDT nodes read per keystroke) and the `editor::collab_keystroke` benchmark. Every peer on a shared document must run a build with quotes in scope before any of them wraps a block in one. Two rules came with it, for every container: **a container emptied by concurrent deletions reads as absent** (`projection::is_void`; two peers deleting a two-item list's items one each used to converge on `<ul></ul>`, which no model can hold), and **a container retyped into one that takes different children is replaced**, never retyped in place (`retype_keeps_identity`; only bullet ↔ ordered keep their identity). Wrapping a block in a quote or lifting it out replaces it, so a peer's concurrent typing in that block is lost, as with a list toggle.

**A textblock reads as its type allows** (#1227). A textblock retyped into another textblock is retyped in place (its `type` key rewritten, its `Text` kept), so a peer's concurrent typing survives a paragraph → code block change; but a peer's concurrent formatting and inline atoms merge into that `Text` too, and a paragraph made a code block while a peer bolds a char and inserts a hard break used to converge on `<pre>a<strong>b</strong>c<br></pre>`. So `projection::build_block` normalises the read the way `Transform::set_block_type` now clears a block locally (`Transform::clear_incompatible`, ProseMirror's `clearIncompatible` with its `linebreakReplacement`): a mark the type does not allow is not read, a `hard_break` in a `NodeSpec::code` block reads as `"\n"`, any other inline node the type does not take is not read (`char_kind`). Every replica reads the same CRDT, so this converges by construction. Nothing is written on read, and the stored text keeps the hidden atoms: a local edit of such a block is diffed **as the block reads** (`projection::TextView`, `kind_in`; `reconcile_read_text`), by the type the model held before the edit wherever that hid an atom, so a converted break compares equal to the model's `"\n"`, a dropped atom is skipped, and the hidden atom stays in place with its `@atom` value (rewriting it into a `"\n"` char on each peer that edits the block left one break per peer, and a diff of the stored text against the model rewrote the block from the edit point on, which concurrent typing duplicated: review of #1846). Stray marks the model does not hold are cleared by that edit's mark resync, so a later retype to paragraph does not bring the bold back. Only a retype that makes a hidden atom readable again (a code block made a paragraph, its stored hard break holding `"\n"` in the model) rewrites that one char, outside the diffed range: two peers retyping the same block out of code at once leave two line breaks there. Sticky indexes map model offsets through the same view (`projection::model_view`), so they resolve in such a block before any write-back, positions after a dropped atom included. Pins: `rinch-editor-collab/tests/code_block_retype_1227.rs`, `tests/fuzz.rs` (`schema_valid` now checks inline content and marks; the 1227 file's randomized trial checks every typed char lands exactly once), `rinch-editor-core/tests/set_block_type_clear_1227.rs`.

**Tables have a wire shape of their own** (`src/table.rs`): a table node carries `cols` and `rows` arrays of id'd maps (deleted ones stay as tombstones) and every cell is keyed by the row and column it starts in, with a span naming its last row and column by id. The read is total and always rectangular (earlier anchor wins, an overlapping span is clipped, an uncovered slot reads as an empty *filler* cell the CRDT does not hold, an emptied cell reads as one empty paragraph, a table with no live row or column is void), and a local edit is projected by matching rows and columns before and after by **model identity** (a row is kept when its `Rc` is; a column when the same cells cover it in every kept row; the changed middle pairs by index) and writing each anchor at its key. Same coordinated upgrade: an older peer meets a node with neither `text` nor `content` and fails loud. Known losses: typing in a row, column or cell a peer deletes or merges away; two peers writing the same filler at once (one cell wins whole); overlapping concurrent merges. The read is bounded (rule 5 in `table.rs`): a table with more slots than the model's `grid_slot_budget`, or more fillers than `max(stored cells, 2^16)`, is not built — a filler costs no wire bytes, and unbounded, a 90 KB update of 2000 rows and 2000 columns read as four million of them (2.3 GB per replica). The model's reads (`to_doc` and the join gate, under `table::placeholder_reads`) see it as a one-cell **placeholder** carrying `table::PLACEHOLDER_ATTR` = the table map's yrs item id (`"{client}:{clock}"`, so two placeholders are never equal), and record it in `CollabDoc::oversized`. **While any such table exists, the editor is frozen**: `EditorCore::commit` refuses every local change exactly as read-only does (`EditorCore::locked`; typing, commands, undo and loads answer `false`, the selection and copy still work, the IME preedit shows nothing), so the model never runs ahead of the CRDT; `CollabSession::record_local` also refuses with `CollabError::OversizedTable` naming the tables; `outbound_stall()` reports it from the moment the table arrives or a guest joins; inbound keeps integrating. **No backlog**: review round 5 showed a kept backlog of frozen edits is wiped by any inbound change (a peer's cure included) and its re-base turns a peer's concurrent delete into deleting another block — the #220 stall's own losses, #1263 and #1264, which the freeze would have made the normal path. Patching routes did not work — rounds 1–4 of #1233's review each found another diff that paired the placeholder with something else and deleted the real table for every peer with `Ok` (a position-paired middle, two equal placeholders matched by value, an HTML/markdown/DocNode export loaded back, which carries no mark) — so no diff ever runs against a placeholder. The cure is `CollabSession::delete_oversized_table(state, id)` / `EditorHandle::collab_delete_oversized_table(id)` (listed by `collab_oversized_tables()`): it removes the table map from wherever it is in the CRDT without reading it (`table::find_table` walks content arrays and cell maps, so a table nested in a quote or a cell is reached), brings the model to the CRDT's read (the placeholder goes, with a container it was alone in; not undoable), and refuses an id not in the current list (a stale id after a peer's shrink would delete a readable table). A peer deleting or shrinking the table lifts the freeze on integrate. `read_model_table` still refuses a marked table (an undo, a paste of a copy). Sticky indexes keep working through a freeze until a local edit is refused (`model_ahead`). Honest peers reach the filler budget (hundreds of rows on one replica and hundreds of columns on another at once); it was a poison at first, which nobody who had seen the table could cure. Both sides also bound **rows + columns** at `max(2 × cells, 2^16)` (#1248): one `colspan = 3_000_000` cell made `start_collaboration_host` write three million column lines; it is now `Unsupported` on write and a placeholder on read, while a host's `colspan = 5000` still reaches its guests whole (`colspan_cap_collab_guest`, #1214). A ragged model table (an app-built transaction's; a paste made one before #1847 padded it, and `splitBlock` at a gap inside a cell before #1232) is refused. **Every child list matches by identity, at every depth** (#1240): `reconcile_node`/`reconcile_child_list`/`reconcile_table` take a `Model` — the node before and after in the model — and take their common leading and trailing runs by `Node::same_ref`, as `project_change` always did at the top level. By value, equal siblings were interchangeable: deleting the first of three empty rows (every fresh `insertTable`), paragraphs in a quote or list items tombstoned the *last*, with a peer's concurrent typing in it. It rests on the editor keeping the `Rc` of every node an edit does not touch (`table_commands_keep_every_row_and_cell_they_do_not_touch` pins it for every table command, #1224's `BatchStep` included) and on no model sharing one `Rc` between siblings. Identity is used only where before and after are **related** (share a child; for a table, a row or cell): `load_doc`/`load_html` while collaborating and the stall-recovery re-base on the CRDT's read-back share nothing, and a level that shares nothing matches by value — at the top level too, an editor's transaction included (Enter at the start of a lone paragraph shares only its text node) — while still handing the model down; under an editor's transaction an atom there is equal only to itself or its kept pair (`equal_under_proof`, node views part C). A table row also matches one that shares a cell (a delete through a rowspan rebuilds the row below), and a column check's changed cell abstains rather than vetoes (a colspan).

**A keystroke in a table cell is projected through that cell** (#1241). `project_change` hands an edit whose one changed top-level block is a table, and whose only change in it is one cell (`table::one_changed_cell`: the table's attrs, every row but one and every cell of that row but one are the same `Rc`s, and that cell keeps its type and attrs), to `CollabDoc::project_cell_edit`, which makes exactly the call the whole-table reconcile makes for such an edit — `reconcile_child_list` on that cell's `content`, with the cell before and after as the `Model` — on the cell map `table::locate_cell` finds, and reads and validates only the cell's blocks. The whole-table reconcile read the CRDT table back twice, built the whole table's target and compared all of it: 26 ms a keystroke at 1000 × 4 cells (93.4M instructions in `editor::collab_table_keystroke.rows_1000`, 32K after). `locate_cell` keeps, per `CollabDoc` (`uid`, in a thread-local because the model table is a `!Send` `Node`), an index of the table's cell maps for one model table at one `CollabDoc::epoch` — a count of the transactions that changed the CRDT, which the update observer bumps for every one, local or remote — so a write not known to leave the table's grid alone makes it be rebuilt (since the follow-up below, an edit elsewhere and a peer's change carry it), and the epoch is compared before any map it holds is touched (a later transaction may have deleted one). A rebuild reads the table once and checks it against the model's read of the table before. The path declines, leaving the edit to the whole-table reconcile, whenever that reconcile would write anything beyond the cell: a filler cell (it has no map yet), a cell two concurrent merges left clipped (the reconcile writes the clip into the CRDT on the table's next edit, `table::stored_as_read`), a cell with no `content` array, an edit whose `related` is not known without walking the table, a cell whose blocks fail the model read (the reconcile reports the error). A table nested in a quote or a cell is still reconciled whole. What is left that grows with the table is the identity scan for the changed row, a pointer compare per row (about 7 instructions), as the top level does per block. The pins: `tests/projection_cost.rs` (`a_keystroke_in_a_table_cell_reads_only_its_block`: one CRDT node read at 10 and at 200 rows), and `tests/table_cell_path_1241.rs`, a differential that runs one random history with the path on and off (`testing::set_table_cell_path`) and compares every peer's CRDT item by item (`testing::same_crdt`) — or, where a link is in play, what each client wrote and deleted (`testing::same_writes`): a char typed after a link is inserted with its formatting, one yrs format item per attribute in a randomly seeded `HashMap`'s order, so two runs of the whole-table path alone build different item ids.

**A peer's change is read back from what it changed** (#1241, after #1871). `CollabDoc::apply_decoded` subscribes a deep observer on the `content` root for the one transaction that applies the update, and keeps the path yrs reports to every shared type it changed (`sync::AppliedChanges`; `Index` segments count an array's live items, `Key` segments name a map key; a type the update created is not there, its parent is), and a plain observer on the `atoms` map marks the record spoiled. It also rechecks `top_void` for the top-level blocks the paths name rather than every block, when the top level held no void container and no path is the root itself. The integrate then calls `CollabDoc::read_changed` instead of `to_doc` when the session knows the model it is handed to be the CRDT's read at the epoch before the update (`atom_cache::synced`, keyed by the model's `Rc` and the epoch: the document the last integrate left, a local edit projected from that document at that epoch — the invariant the local diff already trusts — the document a session started on, or a guest's `projected_doc`, which never displaces an editor's own document at the current epoch). It reads each top-level block a path leads into again with the whole read's own functions (`read_map_data`, `build_node`, the atoms' identities recorded as the whole read records them), and for a table whose paths all lead into cells' blocks (`rows`, row index, `cells`, column id, `content`, …: `table::changed_cells`) only those cells, found by their CRDT key in the table's cell index (`table::places_of`), rebuilt into the cell's own type and attrs; everything else is the model's own `Rc`. The atoms' identities are the model's (`atom_cache`) with each part's spliced in; a document known to hold no atom (`Synced::no_atoms`) counts nothing, and `remote::AtomIds::none` then skips every count in the diff, and the middle walk skips the children a container shares by a pointer compare each. It answers `None`, and the whole read runs as before (it is also the projectability verdict), when only a whole read can say: a path to the root (a top-level block inserted or deleted), an `atoms` entry changed, **a gap in a client's clocks open when the update was applied, or updates parked on missing dependencies** (review of #1926: yrs counts a type as existing before the transaction only below the transaction's `before_state`, and a client's state stops at its first gap — a `Skip` left by an update that arrived ahead of one it follows, or by a merged update with a hole — so while a gap is open a change inside any type its client created after the gap fires no event, whoever makes it, and leaves no path; the partial read then kept a stale paragraph, and a carried cell index read a cell map yrs had collected, a use after free. `CollabDoc::clocks_seen` holds the upper bound of every client's clocks in the updates applied, from `Update::insertions` since `Update::state_vector` stops at a gap too, and a client past its state is an open gap; `tests/skip_1926.rs` holds both repros, and `fuzz.rs` delivers out of order and in merged batches, `fuzz_out_of_order_delivery_converges` and `fuzz_merged_delivery_converges`, with merged cells, cell attributes and swapped rows among the table changes), more than 4096 types, a void container at the top level, an inline atom whose identity the model does not know, a block that fails to read or a table past the read's budget (strict here, so only the whole read records an `OversizedTable`). A local edit whose changed blocks hold an atom, before or after (`CollabDoc::touched_atoms`), forgets the document: an inline atom's identity is what the last read noted for its node, which a write that rewrites its char can leave behind (the atom-identity differentials found it). **The cell indexes are carried** (`table::carry_cell_indexes`): up to eight per document (one per table, newest kept), each true at one epoch and carried to the next by a transaction known to leave its grid alone — the cell path's own write, a local change whose changed blocks do not include the table (`project_change`), an integrate whose paths do not lead into the table or lead only into its cells' blocks (then the index describes the table at that place of the next document) — and an integrate that read a table whole indexes it afresh. An index true at another epoch is dropped **unread**: a map it holds may be gone (deleted and collected), and touching one segfaulted (`Branch::id` on a freed branch) before `keep_index` checked the epoch first. Measured in Callgrind instructions, `editor::collab_table_integrate` 7.67M → 67K at 100 rows and 76.8M → 132K at 1000; `editor::collab_table_keystroke_after_remote` 4.12M → 28K and 40.9M → 35K. What still grows with the table in an integrate is pointer work in the model, about 72 instructions a row at 1000 rows: the transaction's `ReplaceStep` copying the table's and the row's child vectors and dropping the old ones, `Node::resolve`'s scan of the rows, the same copies in `read_changed`, `Event::path`'s walk to the row, the prefix sum of node sizes — what a local keystroke's transaction pays in the editor too. Still a whole read: a peer's Enter or Backspace at the top level (a root path), and any change in a list or a quote, which re-reads the whole top-level block. Pins: `projection_cost::live_collaboration_in_a_table_costs_the_same_at_any_size` (per round, 10 rows against 1000: the nodes an integrate reads, the nodes my next keystroke reads, the index builds; at #1871 it was 4006, 4001 and 1 at 1000 rows), `a_remote_keystroke_beside_an_embed_reads_the_crdt_once` (two nodes per remote keystroke, embed or not), `table_cell_path_1241::the_cell_index_is_kept_until_the_grid_may_have_changed` and `live_collaboration_keeps_the_index_through_each_peer_change`, and the fuzz suites' positive controls (`integrate_reads`: about half their integrates take the partial read). **Every partial read is compared with a whole read** in this crate's debug tests (`testing::set_incremental_read_check`, on by default under `test-util` + `debug_assertions`, the whole read restoring the work counters it moves), so every differential and fuzz test checks it; `testing::set_incremental_read(false)` restores the whole read.

**The inline atoms are the same kind of change, and need the same upgrade.** The format tag did not move for them either, and an older peer reads `@atom` as an unknown mark name. Joining from a snapshot that holds an image or a hard break fails loud (`Schema`, "unknown mark type `@atom` in CRDT"). A **live** older peer whose session integrates one is **poisoned** — `SessionPoisoned`, sticky, inbound *and* outbound — for as long as any atom remains in the shared document, and heals only when the last one is deleted. Measured by the review of #838 against a pre-atom build. So no peer may insert an image or press Shift+Enter until every peer runs a build with inline atoms in scope.

**Per-attribute atom attrs are a third such change** (#1503). An atom's attr change is an entry of a new root map `atoms` (`"<identity>/<attr>"`) and marks the atom's char with the reserved formatting attribute `@entries`; a move (Enter or Backspace before a picture in its line, a drag) writes the reserved keys `@id` and `@for` into its `@atom` value. A build from before refuses both (`Schema`, "unknown mark type `@entries`" / "unknown reserved key `@id`"): joining fails loud and a live older peer is **poisoned**, and stays so for that document. Inserting, typing around, marking and deleting atoms wrote the old shape until #1851; **since #1851 every atom a build writes carries `@for` (its own char), so a build before #1503 refuses a document holding a newly inserted atom** (a picture, a hard break) and is poisoned on it: every peer on a document must run a #1503 build before any of them runs #1851, and the old guarantee that inserting atoms writes the old shape is gone (see **Equal atoms never share formatting markers** below). The mark is a separate attribute, not a key in the `@atom` value, because yrs can extend a formatted range over a peer's concurrent insert at its edge, and a value naming an identity that leaked onto a neighbouring picture showed that picture as this one (differential seed 208). So every peer must run a build with #1503 before any of them changes an image's attrs or moves one (`crates/rinch-editor-collab/src/atoms.rs`, *What a build from before reads*).

**Node views are a fourth such change, without a wire change** (node views part B). The bytes did not move, but what a CRDT block *means* did: a build with node views writes an embed (any leaf block atom) put where a different model node stood as a **new block** (`record_local_keeping`), and its receiver keeps a view mounted only on the same block (`remote::AtomIds`). A peer built before writes such an atom positionally — a moved or swapped embed takes over the old one's block, attributes and all — so a newer peer reads it as an attribute change and its view keeps its mount while showing **the other embed's attributes** (`review_1575_node_views::r11_an_older_peer_swapping_two_embeds_hands_views_the_other_nodes_data` pins the limitation). Nothing fails loud: every peer on a document must run a build with node views before any of them moves an embed an app draws.

**The atom attribute is resynced per char, not per span.** yrs extends a formatted range over an insert at its end boundary, so a char typed right after an image lands inside the image's `@atom` range. A per-span resync then cleared and rewrote the image itself, and that fresh write reverted a peer's concurrent `src` change on every replica (the #193 resurrection shape; review of #838). `resync_atoms` in `projection.rs` clears only the stray chars, and writes every char the splice inserted with its own whole value, named for its own char (so a picture or a hard break inserted right after a picture is a value of its own, not a copy of its neighbour's); `resync_per_char` does the same for every non-inclusive mark (`link`, which yrs extends over a char typed after it the same way — though a char typed after a link is now inserted outside it in the first place, see **Inherited marks** above), and every other mark stays per span. **An atom's attrs merge per attribute** (#1503, `src/atoms.rs`): an attr change is one entry of the root map `atoms` under the atom's identity (its char's yrs id, or the `@id` a move carried), laid over the `@atom` value on read, so two peers changing different attrs of one image (`alt` and an app's `data-*` attribute, `title` and `width`) both keep their change, and two changing the same attr converge on the higher client id's — except `src`: a `src` change makes a new picture (below), so a peer's concurrent change of the old one is lost. **An identity stays on its atom**, because an app keys its own data to a picture through its attributes, and that data shown on another picture is worse than lost: the text diff matches a placeholder only with the same model atom (`text_splice_bounds`: `Node::same_ref`, since the editor keeps an unchanged node's `Rc`; a new node at the same place is an attr change only when the editor **proves** it — its transaction only set that node's attributes, a `SetNodeAttrStep` handed over through `CollabSession::record_local_keeping` — and it keeps its type and `src`: decision (f), Joe 2026-10-19), and a move carries the identity to the new char only when the model says it is the same atom (`atoms::carry_over`). So a peer's concurrent change of a picture's attrs survives Enter or Backspace anywhere in its line, a drag, a picture inserted before or after it, a copy of it pasted elsewhere and a deleted neighbour, and two identical adjacent pictures are two identities (#860's loss is gone). `tests/atom_identity_differential.rs` runs random histories and concurrent edits and asserts an app's `data-*` attribute never shows on another picture (60 seeds by default; at 1000 seeds, 1978 checks: none wrong; 46 lost, every one to a concurrent `src` change of the picture, by design; 12 where both peers moved the picture at once and it is doubled, the attribute on both copies of it; the code before this measured 9 wrong in 290), and `tests/atom_identity_identical_pictures.rs` does the same with identical pictures, three peers (one reconciling through `sync_diff`), undo/redo, cut and paste and hard breaks (1000 seeds: 2000 checks, none wrong, 233 lost — cut-and-paste 90, undo of a delete 84, copy-then-move 40, undo/redo 19 — and none doubled: before the (old, new) proof, 2 were, seed 785, where one peer pasted over a picture while the other changed one of two copies of it and wrote that proved change as a new char too (review 2 of #1595, G2); review 2's head measured 4 wrong in 600, and a model holding one picture `Rc` in two blocks once made 2 wrong, seed 975, pinned by `seed_975_one_picture_rc_in_two_blocks_names_no_other_picture`; both differentials record through `record_local_edit` with the proof an editor gives, `testing::kept_atom_pairs`, and the identical-pictures oracle counts TARGET on a picture pasted over the target as wrong; its oracle maps the target through B's transactions, so a rebuild plus a reorder in one step cannot name another picture as the target). **A value written over a char names the char it is for** (`@for` beside `@id`, honoured only on that char), and no value written over an existing char holds changed attrs: yrs extends a formatted range over a peer's concurrent insert at its edge, and before this a picture inserted beside a moved or edited-apart one took its identity and its attributes (review 2, R2-1). **A `src` change makes a new picture**, proved or not: before decision (f) the model could not tell it from a picture pasted over a selected one, and keeping the identity through it showed a peer's attribute on the pasted picture. Chosen by Joe (2026-10-09): a wrong attribution is worse than a lost one — app data keyed to a picture would show on the wrong picture. An app that inserts a picture only once its final `src` is known, and writes a fresh copy rather than changing a live picture's `src`, loses nothing to it (`a_src_change_drops_a_concurrent_alt_change`, `a_data_ref_never_lands_on_a_picture_pasted_over_its_own`). **What is left:** a peer's concurrent change of a picture whose `src` is changed, or that is pasted over, is lost, and so is one of a picture cut and pasted back or deleted and restored by undo (a later transaction re-inserts it as a new picture; only a move within one transaction carries its identity), and one of a picture dragged after an in-editor copy of it (the two are one `Rc`, so `carry_over` carries neither) until either copy is changed; a picture pasted over another is a **new** picture whatever its `src` (decision (f): identity only where the editor proves an attr-only edit, `kept_inline`), so a peer's concurrent change of the old one is lost, never shown on the pasted one, and a peer's node view drawn for the old one is remounted rather than handed it (a caller driving `CollabSession::record_local` itself, without the proof, keeps the older type + `src` rule); two peers who each truly replace one picture at once (a paste over it, a drag) keep both pictures, ordinary CRDT replace/replace behaviour, like two people typing over one selected word; a move into or out of a table cell, and an attr change made by a load or a re-base (whose documents share no node), lose a peer's concurrent change; two peers moving one picture at once make two copies that both carry its identity until one is changed (`two_copies_from_concurrent_splits_are_edited_apart`); and the entries of a deleted picture are never collected (a few dozen bytes each; see `atoms.rs` *Growth*). The read of the `atoms` map is once per operation (`atoms::overlay_scope`; it was once per block holding an atom, which made a remote keystroke quadratic in edited pictures), pinned by `projection_cost::a_keystroke_reads_the_atom_entries_once`. `tests/image_attrs.rs` and `tests/atom_attr_merge.rs` pin the round trip, the merges and the wire shape.

**Equal atoms never share formatting markers** (#1851). yrs coalesces equal formatting, so two equal atoms side by side (two hard breaks, a picture inserted twice) shared one start and one end marker, and an atom inserted right after an equal one had none of its own. yrs's `remove` (`clean_format_gap`) and its transaction-end cleanup delete the markers they find redundant, and a concurrent edit that relied on them lost its atom, which read back as a literal U+FFFC character: `<p>a<img>x<img>b</p>` with A deleting `x` while B types after the first picture converged on `a[image]y￼b`; a break inserted after a break whose line a peer deleted, the same. Every atom's `@atom` value now names its own char (`@for`, no `@id`: `atoms::write_own_value`, at every write of a new atom: `resync_atoms`, `write_node`), so no two values are equal and each atom has markers of its own; a reader takes `@for` without `@id` as no carried identity. Atoms written before #1851 keep their shared markers until rewritten. Pins: `tests/typed_once_1850.rs` (`typing_between_two_pictures_*`, `a_break_inserted_beside_*`, and the randomized trial: 0 literal U+FFFC in 1000 seeds, 14 before).

**Where a split or a join puts its new block** (#1850). The projection has no move: a block reconciled in place keeps its chars' CRDT identity, and text that ends up in a block on the other side of the inserted or deleted one is deleted and written again, so a peer's concurrent edit of that text lands on the old copy (lost, or the text arrives twice). The changed run of a child list puts the blocks it inserts or deletes where its pairs keep the most text in place (`write_child_diff`, `gap_of_least_moved_text`; ties keep the old answer, the extra blocks at the end of the run): Enter at the start of a line inserts the empty block before it and keeps the line's text in place (it used to copy the whole line into a new block, and two peers pressing Enter there left the line twice), Backspace at the start of a line after an empty one deletes the empty one, a split keeps its longer half and writes the shorter one anew, and a join keeps the block holding more of the joined text. A peer's concurrent edit of the half that moved lands on the old copy: a char typed at the start of a line split in its middle, head shorter than tail, follows the tail (`blockquote.rs`, `editing_next_to_a_void_quote_projects_around_it`). Concurrent moves of the same text still duplicate it, since each copy is a fresh write: two peers pressing Enter at the same place, both joining the same two lines, a join while the other splits the second line, an undo re-inserting a cross-block delete while a peer moves that text. The randomized trial (`tests/typed_once_1850.rs`) measures 104 seeds in 1000 with a duplicated char before and 39 after, and pins that as a ceiling; storing blocks as boundary markers in one shared text is the design that removes the rest (#1857).

**An A22-refused local edit stalls outbound, it does not wedge it (#220).** The
model applies the edit even though the CRDT refuses it, so from that moment the
caller's `before` no longer describes the CRDT. `record_local` therefore treats
`before` as a *hint*: if diffing against it fails, the change is re-projected
against the CRDT's own read-back, which is authoritative. That is what makes the
recovery real — before, the block-count gate refused **the very deletion that was
the cure**, and once the counts realigned by coincidence the diff skipped the
blocks it believed unchanged, so an edit made during the stall stayed local
forever while `record_local` answered `Ok`. Silent divergence. Now removing the
offending content resumes outbound on the spot and ships the whole backlog in one
delta. `record_local` takes the `&Schema` for the read-back (a session cannot hold
an `Rc<Schema>` — it must stay `Send`); `collab_outbound_stall()` reports the
state while it holds.

**Collab bytes are opaque.** A snapshot, a broadcast delta, a state vector, and a sync diff are all just `Vec<u8>` in yrs's lib0 v1 encoding — callers move them between calls without decoding them.

```rust
use rinch_editor_collab::CollabSession;

// One session per editor. Peer B joins from peer A's snapshot.
let mut a = CollabSession::new(&state)?;            // project state.doc onto a fresh CRDT
let mut b = CollabSession::from_bytes(&a.snapshot())?;

// After the editor applies a local transaction, project before→after onto the CRDT:
a.record_local(new_state.schema(), &old_state.doc, &new_state.doc)?;

// Broadcast a delta:
let delta = a.save_incremental()?;
if let Some(next) = b.integrate_incremental(&b_state, &delta)? { b_state = next; }
// `next` applies the remote change as a non-undoable `origin=remote` transaction.

// Reconciliation for a peer that fell behind (offline, a dropped delta):
let to_b = a.sync_diff(&b.state_vector())?;   // "what does b not have yet"
if let Some(next) = b.integrate_incremental(&b_state, &to_b)? { b_state = next; }
```

**The desktop editor wires this in for you** (M9) — you do not drive `CollabSession` directly. Every local edit through an `EditorHandle` projects + broadcasts automatically; a peer's delta integrates + re-projects through `collab_receive`. One peer **hosts** (owns the starting document), the others **join** from its snapshot. The transport is the app's concern — `outbound` carries bytes out, `post_remote_delta` carries them back in from any thread:

```rust
// Host: project the current doc onto a fresh CRDT, hand peers a join snapshot.
let snapshot = host.start_collaboration_host(move |delta| transport.send(delta))?;
// Guest: adopt the host's document and collaborate.
guest.start_collaboration_guest(&snapshot, move |delta| transport.send(delta))?;
// Inbound from a network thread (marshals onto the main thread); from the prelude:
post_remote_delta(container_id, delta_bytes);
```

Free functions `collab_receive_for(container_id, &delta)` (main thread) and `post_remote_delta(container_id, delta)` (any thread) route an inbound delta to a registered editor. Runnable two-pane in-process loopback: `examples/collab-editor-demo`.

**The transport owns relaying.** `outbound` fires only for an editor's own local edits — a delta integrated via `collab_receive` is never re-broadcast (it's already in the shared CRDT; echoing it back would loop). So the transport must be a **full mesh** (every peer's `outbound` reaches every other peer) or a **hub** that fans each delta it receives out to the others, forwarding the raw bytes unchanged. A chain — A wired to B, B wired to C, nothing joining A and C — silently partitions: C never sees A's edits, and nothing errors. The repair for a peer that fell behind is the reconciliation pair above (`collab_state_vector` → `collab_sync_diff` → `collab_receive`).

**Never use state-vector equality as a convergence test.** A yrs state vector counts *insertions* only — a deletion, or a mark *removal* (yrs un-formats a mark by deleting its format marker), leaves it unchanged, so two replicas can hold different documents behind equal state vectors. That's why `integrate_incremental`/`collab_receive` decide "did anything change" by rebuilding and comparing documents, never by comparing state vectors before/after — and why reconciliation always requests-and-applies a diff (whose reply carries the full delete set) rather than short-circuiting when two state vectors look equal.

`CollabPlugin` (key `"collab"`) folds collab bookkeeping (version + unconfirmed local steps) into `EditorState`; `rebase_steps(steps, &mapping)` is the ProseMirror rebase primitive (`Step::map`). The session integrates by converged rebuild (`CollabDoc::to_doc` → `build_remote_transaction`), which is provably convergent — there's no separate patch→op translation layer. Since #1241 the rebuild reads back only the blocks (or table cells) the update changed whenever the model is known to be the CRDT's read from just before it (above, *A peer's change is read back from what it changed*): still a read of the converged CRDT, of less of it, and equal to the whole read, which every debug test of the crate checks. One used to exist (`CollabDoc::patches_to_remote_ops`/`remote_ops_since`, consuming `automerge::Patch`) but it was **deleted**, not ported, with the yrs migration: it was documented as non-convergence-critical and had no session consumer. `remote.rs`'s module doc notes it could be rebuilt on yrs observer deltas (`TextRef::observe` → `TextEvent`) if a future cursor-preserving refinement ever wants it.
